# EPIC-028 — Incidents & Alerts Triage

- **Status:** Drafted
- **Cluster:** Security
- **Severity:** high
- **Depends on:** EPIC-002, EPIC-006, EPIC-029
- **CIPP provenance:** [`cipp-features.md`](../../99-reference/cipp-features.md) #17; CIPP `Security/Incidents/`
- **Epic ticket:** [`epic.md`](epic.md)

## 1. Purpose

Triage security incidents and alerts across Defender, Defender for Office 365 (MDO), and Graph
security alerts: review, assign, comment, and change status. The module already reads incident
readiness (`Get-StrykerIncidentReadiness`) and Defender state; this epic adds the triage workflow.

### Planned scope

- Incidents list + detail
- Security/MDO/Defender alerts
- Set alert/incident status (gated)
- Check-alerts integration

## 2. User stories

| # | Story | Candidate child ticket |
|---|---|---|
| US-1 | As an analyst, I can list and filter open incidents across tenants. | `T-IC-01` incident list |
| US-2 | As an analyst, I can open an incident and see its alerts, entities, and timeline. | `T-IC-02` incident detail |
| US-3 | As an analyst, I can assign, comment on, and change an incident's status. | `T-IC-03` triage actions |
| US-4 | As an analyst, I can triage MDO/Defender alerts individually. | `T-IC-04` alert triage |

## 3. UI design

Nav: *Security & Compliance → Incidents & Alerts* (Incidents, Alerts, Defender Alerts, Check
Alerts) ([`cipp-ui-inventory.md`](../../99-reference/cipp-ui-inventory.md) §3). Theme per
[`02-ui-design.md`](../../00-guides/02-ui-design.md).

### 3.1 Incidents list (US-1)

Page title: **Incidents**.

- **Table:** Title · Severity (`sev-badge`) · Status · Classification · Assigned to · Alerts ·
  Last updated · Tenant.
- **Filters:** severity, status, classification, assigned, date, tenant (all-tenants view).
- **Row actions:** `View`, `Assign`, `Set status`, `Classify`, `Comment`, `Resolve`.
- Bulk actions: assign, set status (with confirmation).

### 3.2 Incident detail (US-2, US-3)

Tabs: **Overview** (severity, status, classification, assignee) · **Alerts** (linked alerts) ·
**Entities** (users/devices/mailboxes involved) · **Timeline** (events + comments) ·
**Notes** (portal comments). Triage actions in the header.

### 3.3 Alert triage (US-4)

Page title: **Alerts**. Table: Title · Service source (Defender/MDO/Graph) · Severity · Status ·
Entity · Created. Row actions: `View`, `Set status`, `Assign`, `Comment`, `Create incident` (where
supported).

### 3.4 Check alerts (US-5)

Page title: **Check Alerts** — the module's own alert findings (e.g. from checks) shown alongside
tenant alerts so analysts see portal-detected issues in the same view.

## 4. Workflows

### 4.1 Triage (US-3, US-4)

1. Analyst opens an incident/alert.
2. Sets status (`new` → `in progress` → `resolved`), classification (true/false positive,
   informational), assignee, and comments.
3. Each change is a tenant write routed through **EPIC-006** (confirm where impactful), audited.

### 4.2 Cross-tenant view (US-1)

The all-tenants view aggregates open incidents by severity, respecting RBAC scope.

### 4.3 Check alerts (US-5)

Check alerts are generated by EPIC-029's rules and/or the module's checks; they are displayed and
can be snoozed/resolved (handled in EPIC-029).

## 5. Data model

| Entity | Fields | Notes |
|---|---|---|
| `IncidentNote` | `id`, `tenantId`, `incidentId`, `body`, `author`, `at` | portal-side comments |
| `AlertStateChange` | `id`, `tenantId`, `alertId`/`incidentId`, `from`, `to`, `by`, `at`, `reason` | triage audit |
| `AuditEvent` | full shape | every write |

Incidents/alerts are read live from Graph/Defender; portal notes and state changes persist.

## 6. API surface

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/v1/tenants/{id}/incidents` | list |
| `GET` | `/v1/tenants/{id}/incidents/{incidentId}` | detail |
| `POST` | `/v1/tenants/{id}/incidents/{incidentId}/{action}` | assign/status/classify/comment |
| `GET` | `/v1/tenants/{id}/alerts` | alert list |
| `POST` | `/v1/tenants/{id}/alerts/{alertId}/{action}` | triage |
| `GET` | `/v1/check-alerts` | module check alerts |

## 7. Permissions & scopes

- **RBAC:** `incidents.read`, `incidents.triage`; triage writes require `Remediation.Apply`
  semantics. Tenant-scoped (EPIC-038).
- **Tenant auth:** Graph `SecurityEvents.ReadWrite.All`, `SecurityAlert.ReadWrite.All`.

## 8. Remediation behavior

Status/classification/assignment changes are tenant writes and route through **EPIC-006**
(confirmation for bulk, before/after, audit). Read views perform no writes.

## 9. Dependencies & risks

- Depends on EPIC-002 (tenants), EPIC-006 (writes), EPIC-029 (check alerts).
- **Risk: bulk status changes hiding real incidents.** Mitigation: confirmation, audit, no silent
  auto-resolve.
- **Risk: alert volume.** Mitigation: filters, severity/status grouping, snooze via EPIC-029.
- **Risk: source divergence** (Defender vs Graph alert shapes). Mitigation: a normalized alert
  model in the UI.
