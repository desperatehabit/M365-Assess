# T-0842 — App package ingest and signed download routes

## Report

T-0322's `AppPackageStore` streams a package onto the artifact tier and mints signed,
short-lived URLs; T-0323's upload route takes an already-stored `packageId` and its job runner
hands the worker a signed URL on `/v1/app-packages/:packageId`. Neither end has an HTTP route,
because `server.ts` reads every body as JSON (capped at `MAX_JSON_BODY_BYTES`) and a
`RouteResponse` carries only a buffered `raw` payload.

1. **Streaming seam in `server.ts`.** Let a route opt in to the raw request stream (skipping JSON
   parsing and its body cap) and return a `Readable` response body with a content length.
2. **`POST /v1/tenants/:tenantId/apps/packages`** (`app-packages.ts`): stream an
   `application/octet-stream` body into `AppPackageStore.storePackage`, honouring
   `Content-Length` as the declared size and taking the display name from `?fileName=` (the
   T-0326 wizard sends it that way), behind `Endpoint.Application.ReadWrite` or
   `Remediation.Apply`. Return `{ packageId, fileName, size, sha256 }`; never a path.
3. **`GET /v1/app-packages/:packageId`**: authenticated only by the signed query
   (`verifySignedUrl`); 403 when tampered, 410 when expired; stream via `openPackage`.
4. **Config:** `M365_BFF_APP_PACKAGE_SECRET` (≥ 32 bytes; refuse to start the package routes
   without one), `M365_BFF_APP_PACKAGE_MAX_BYTES`, and the base URL workers use to reach the BFF.
5. **Job type:** add `app-upload` to `JOB_TYPES` so the T-0323 runner can go through the
   EPIC-001 queue and emit the standard `ProgressEvent`s.

## Acceptance

- [x] A package upload streams to the artifact tier without buffering the whole body, and the size cap cuts it off with 413.
- [x] The download route serves a package only for a valid, unexpired signature and streams it.
- [x] The signing secret is required configuration and never appears in logs, responses, or events.
- [x] `app-upload` is a valid job type in the contracts.
- [x] Tests cover the seam and both routes and fail without them.
- [x] No file outside `scope` is modified.

## Resolution

- **Seam** (`server.ts`): a route may set `rawBody: true` to skip JSON parsing and its 1 MiB cap
  and receive `ctx.requestStream`; such responses carry `Connection: close` so an early error
  never has to drain an unread upload. A `RouteResponse` may return `stream` (+ `contentLength`),
  which the server pipes; a read error mid-stream destroys the connection so the client sees a
  failure, never a short "success".
- **Routes** (`app-packages.ts`): `POST /v1/tenants/{id}/apps/packages?fileName=*.intunewin`
  (octet-stream only, 415 otherwise; `Content-Length` over the cap is 413 before reading; a
  chunked upload is cut off at the cap; audited; returns id, name, size, sha256) and
  `GET /v1/app-packages/:packageId` authenticated solely by the signed query (403 / 410 / 404),
  streamed with `Cache-Control: no-store` and an `X-Content-SHA256` header the worker can check.
- **Config**: `M365_BFF_APP_PACKAGE_SECRET` (≥ 32 bytes, error names the variable, never the
  value; null leaves the package routes for T-0844 to leave unmounted),
  `M365_BFF_APP_PACKAGE_MAX_BYTES` (default 8 GiB), `M365_BFF_WORKER_BASE_URL` (default
  `http://<host>:<port>`, reduced to its origin).
- **Contracts**: `app-upload` added to `JOB_TYPES`.
- **Scope extension — latent bug fixed:** `routes/runs-artifacts.ts` (T-0048) already returned
  its download as a `stream` field that the server ignored, so in production
  `GET /v1/runs/:runId/artifacts/:name` answered 200 with a JSON `null` body; only tests that
  injected a raw `res` ever saw bytes. With the seam the stream is piped. The one-file change
  types the field as `Readable` and moves `Content-Length` / `Content-Disposition` onto the
  response (they were only ever set on the injected `res`).
