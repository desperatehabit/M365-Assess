# T-0012 — Run lifecycle API and persistence

## Report

EPIC-001 SPEC.md §4.3 and §6 define the run lifecycle and the v1 endpoints:
`POST /v1/tenants/{tenantId}/runs`, `GET /v1/runs/{runId}`,
`GET /v1/runs/{runId}/results`, `GET /v1/runs/{runId}/artifacts/{name}`,
`POST /v1/runs/{runId}/cancel`. Run creation supports `Idempotency-Key`; results use cursor
pagination; every write is tenant-scoped by the caller's RBAC scope.

Deliver:

- Route handlers implementing the five endpoints, writing `Run`/`RunSection`/`Finding` through
  the repository (T-0009) and enqueuing jobs through the queue (T-0010).
- `POST` accepts `Idempotency-Key` and returns the existing run on replay.
- Artifacts are served from the artifact path recorded on the `Run`; artifacts are referenced,
  never held in memory.
- OpenAPI document updated to match the implementation exactly.

## Acceptance

- [ ] All five endpoints are implemented and match the OpenAPI document.
- [ ] A replayed `Idempotency-Key` returns the original run and does not enqueue a second job.
- [ ] A run over 2+ tenants persists `Run`/`RunSection`/`Finding` and serves results paginated.
- [ ] Requests for a tenant outside the caller's scope return a structured error.
- [ ] No file outside `scope` is modified.
