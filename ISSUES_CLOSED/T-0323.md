# T-0323 — App upload queue worker and queue status API

## Report

EPIC-017 SPEC.md §3.2 and §4.1 describe the upload path: the wizard stores the package and
queues a job; the queue performs the Graph content upload and commit in the tenant's process;
progress is visible on the Queued Applications page; failures are re-runnable. §6 fixes
`POST /v1/tenants/{id}/apps/upload` and `GET /v1/tenants/{id}/apps/queue`, and §3.2 says queue
tracking reuses EPIC-003/EPIC-007's job progress.

Deliver `Queue-IntuneAppUpload.ps1` + `queue-intune-app-upload.ps1`, a job handler that resolves
the T-0032 signed package source, uploads and commits the app to Graph, and records state on the
`AppDeployment` row (T-0322). The BFF route enqueues through the EPIC-001 queue (T-0010) and
serves queue status from persisted deployment records, so a failed item can be re-run. Graph
writes route through EPIC-006's gated executor semantics; each transition is audited.

## Acceptance

- [x] `POST /v1/tenants/{id}/apps/upload` enqueues a job and returns a deployment id; `GET .../apps/queue` reports per-item state.
- [x] The worker uploads and commits the package and records `state`/`results`; a failed item is re-runnable.
- [x] Progress is observable through the existing queue/progress contract; no secret or package bytes appear in events.
- [x] Tests cover the route and worker and fail without them.
- [x] No file outside `scope` is modified.

## Resolution

- **Routes** (`intune-apps-queue.ts`): `POST .../apps/upload` validates the wizard request
  (win32: stored `packageId`, commands, run-as, restart, architectures, detection rules; store:
  `packageIdentifier`), supports `preview`, persists an `AppDeployment`, audits, and enqueues a
  reference-only job. `GET .../apps/queue` reads the rows. A re-run route,
  `POST .../apps/queue/:deploymentId/rerun`, re-queues a `failed` item (SPEC §9); §6 does not
  list it, but the acceptance needs re-runnable items to be reachable.
- **Runner** (`runAppUploadJob`): moves the row `queued → uploading → committing → succeeded`
  or `→ failed`, audits each transition, mints the signed package URL, and keeps the worker's
  `appId` so a re-run reuses the Graph app. The queue is a port (`AppUploadQueue`) and progress
  is a scope-local `AppUploadProgress`, because the contracts `JobType` list has no app-upload
  type yet.
- **Worker** (`Queue-IntuneAppUpload.ps1`): the Graph win32 content-upload sequence (beta
  `mobileApps`), and a single `winGetApp` create for store apps. Download size and sha256 are
  checked before any Graph write; SAS URIs and URL signatures are redacted from errors; the
  encryption info goes only to the commit call.
- **Not verified live:** every Graph call is mocked, as with EPIC-016 (compare T-0814).
- **Follow-up:** T-0842 adds the streaming server seam, the package ingest and signed download
  routes, the signing-secret config, and the `app-upload` job type.
