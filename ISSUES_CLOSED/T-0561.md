# T-0561 — Alerting storage: rules, events, channel config, and webhooks

## Report

EPIC-029 SPEC.md §5 fixes the alerting entities: `AlertRule` (`id`, `name`, `source`,
`conditions[]`, `actions[]`, `enabled`, `scriptMode`, `scheduleId`), `AlertEvent` (`id`, `ruleId`,
`tenantId`, `firedAt`, `severity`, `payload`, `state`, `snoozeUntil`), `NotificationConfig`
(`id`, `channel`, `target`, `enabled`), and `WebhookRule` (`id`, `url`, `match`, `enabled`).
[`03-database.md`](../../docs/portal-specs/00-guides/03-database.md) §5 requires soft delete for
alert records so history survives deletion, and §6 requires every mutation to write an audit event.

Deliver migration `0050_alerting.sql` (numbered, forward-only, advancing `SchemaVersion`) plus a
repository module with CRUD and query methods for all four entities, and the shared contract types
in `portal/contracts/src/alerting.ts`. `AlertRule.conditions`/`actions` are stored as validated
JSON. Tenants come from EPIC-002 (T-0021); the `tenantId` column is a foreign key to that table,
a data dependency handled in prose, not a code dependency.

## Acceptance

- [ ] Migration 0050 applies after the foundation migrations, is re-runnable, and advances `SchemaVersion`.
- [ ] The repository round-trips every field in the §5 `AlertRule`, `AlertEvent`, `NotificationConfig`, and `WebhookRule` shapes.
- [ ] Alert records soft-delete (`deletedAt`) and are excluded from default queries; deletions are auditable.
- [ ] `conditions`/`actions` reject malformed JSON with a structured error.
- [ ] A test covers the repository and fails without it.
- [ ] No file outside `scope` is modified.
