# T-0893 — RBAC registry and permission taxonomy cover the newly mounted Purview, SharePoint and Mailbox routes

## Report

Newly mounted routes use `purview.read/write/templates`, `sharepoint.read/write/cleanup` and ~25 mailbox permissions that do not follow the `{Area}.{Resource}.{Read|ReadWrite}` taxonomy and (for Purview and Mailboxes) are absent from `PermissionRegistry`. Non-superadmin roles may get 403 on every endpoint; `rbac/permissions.test.ts` already fails on main and fails more with these routes mounted. Rename the permission strings to the taxonomy (route modules, tests, SPEC §7), register them in `PermissionRegistry`, regenerate `portal/contracts/openapi/portal.v1.yaml`, and make `rbac/permissions.test.ts` pass.

## Acceptance

- [ ] The behaviour described in the report is fixed.
- [ ] A test covers it and fails without the fix.
- [ ] No file outside `scope` is modified.

## Resolution

Renamed the lowercase per-epic permission strings to the `{Area}.{Resource}.{Read|ReadWrite}` taxonomy, kept high-privilege operations as documented admin-only names, registered all mounted Mailbox, Purview, Safe Links, compliance-template, user, role and destructive device-action routes in `PermissionRegistry`, regenerated `portal.v1.yaml`, and updated SPEC references. `rbac/permissions.test.ts` passes 18/18 and `route-permissions.test.ts` checks each handler enforces its registered permission. Open finding: `/v1/api-clients` CRUD and rotate-secret perform no authorization check (filed as a follow-up).
