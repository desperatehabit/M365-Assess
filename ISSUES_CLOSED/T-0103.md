# T-0103 — RemediationPlan, RemediationAction, and ManualInstruction entities

## Report

EPIC-006 SPEC.md §5 fixes three entities that must persist before any plan or apply path exists:
`RemediationPlan` (`id`, `tenantId`, `runId`, `findingIds[]`, `mode`, `createdAt`, `createdBy`),
`RemediationAction` (`id`, `planId`, `checkId`, `command`, `target`, `state`, `before`, `after`,
`appliedAt`, `appliedBy`, `result`, `error`, `correlationId`), and `ManualInstruction`
(`checkId`, `portalPath`, `steps[]`, `notes`). `RemediationAction.state` ∈
`planned | approved | applied | failed | skipped`; `RemediationPlan.mode` ∈
`manual | automated | mixed`. Audit is append-only (SPEC §8).

Add the next forward-only migration under `portal/db/migrations/` (pick the next free number for
this worktree), a `remediation-repository.ts` implementing the SPEC §5 shape, and extend the
repository interface/index so later tickets can create plans, read a plan with its actions,
list actions by plan/tenant, and update one action's state/before/after/result. No writes to a
tenant happen here.

## Acceptance

- [ ] Migration is forward-only and creates the three entities with the SPEC §5 columns.
- [ ] Repository round-trips a plan + actions and rejects an invalid `state`/`mode`.
- [ ] `RemediationAction` rows are append-mostly (updates record `appliedAt`/`result`, no deletes exposed).
- [ ] A test covers the change and fails without it.
- [ ] No file outside `scope` is modified.
