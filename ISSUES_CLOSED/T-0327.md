# T-0327 — ApplicationTemplate persistence, CRUD, and variable-substituted deploy

## Report

EPIC-017 SPEC.md §3.3 defines **Application Templates** and requires deploy with variable
substitution (e.g. package paths, group names). §5 adds `ApplicationTemplate` (`id`, `name`,
`appType`, `config`, `variables`) and §6 fixes `GET`/`POST`/`PATCH`/`DELETE /v1/app-templates`
plus the deploy call.

Deliver migration `0083_application_templates.sql`, an `application-templates.ts` repository
behind the ADR-0015 interface, CRUD routes behind RBAC `intune.apps`, and a
`Deploy-ApplicationTemplate.ps1` + entrypoint that substitutes template variables (reusing the
EPIC-002 `%var%` substitution semantics) into the T-0322 deployment path and returns per-target
results with partial failures. Each deploy is audited with before/after.

## Acceptance

- [x] A migration creates `ApplicationTemplate`; CRUD round-trips the §5 fields.
- [x] Deploy performs variable substitution and reports per-target results including partial failures.
- [x] `appType` is validated against the T-0321 registry; invalid input returns a structured error.
- [x] Tests cover the routes and worker and fail without them.
- [x] No file outside `scope` is modified.

## Resolution

- **Migration** `0083_application_templates.sql` (the ticket named `0016`, which sorts before
  applied migrations, and `0041`; next free number). Templates are portal-wide with a
  case-insensitive unique name. The repository rejects unsupported `appType`s, configs over
  64 KiB or carrying credential-like keys, and malformed or duplicate variables. It is tested
  through the route tests (no repository test file is in scope).
- **Routes**: `GET`/`POST /v1/app-templates`, `GET`/`PATCH`/`DELETE /v1/app-templates/:id`,
  and `POST /v1/app-templates/:id/deploy`. Reads need `Endpoint.Application.Read`; template
  writes `Endpoint.Application.ReadWrite`; deploy that or `Remediation.Apply`. Every write is
  audited with before/after.
- **Variables**: per tenant, template default < global < tenant < the request's `values`, with
  EPIC-002 `%name%` semantics (unknown token fails the target). A token that resolves to a
  **secret** tenant variable fails the target and never reaches the worker, because the
  substituted request is persisted on the AppDeployment row.
- **Packages across tenants**: packages are tenant-scoped on the artifact tier, so a Win32
  template names its package through a variable (e.g. `%SevenZipPackage%`) set per tenant,
  which is the SPEC §3.3 "package paths" substitution. Deploy checks the package exists on
  that tenant's tier.
- **Worker** (`Deploy-ApplicationTemplate.ps1`) is a read-only preflight: it substitutes the
  resolved values and reports an existing app of the same name as a conflict. The BFF then
  validates the request as a T-0323 upload, persists the AppDeployment (with `templateId`),
  audits, and queues it.
- **Deploy results** are per target (`planned`/`queued`/`failed` with the error), so partial
  failures show; multi-tenant apply requires `confirmTargetCount` (§8).
