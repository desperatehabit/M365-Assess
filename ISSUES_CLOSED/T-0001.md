# T-0001 — RunContext type and New-RunContext factory

## Report

EPIC-001 SPEC.md §4.1 fixes the target shape: one `RunContext` object threading tenant, auth,
scope, output, service/registry/issues state, and paths, replacing the ~20 caller-scope
variables and `$script:`/`$global:` run state that `Connect-RequiredService.ps1` reads
implicitly (EPIC-001 SPEC.md §4.1 table; `docs/portal-specs/00-guides/01-architecture.md` §4).

Deliver:

- A `RunContext` class with the member groups in SPEC §4.1 — immutable config (`Tenant`,
  `Auth`, `Scope`, `Output`, `Paths`) and mutable run state (`Services`, `Registry`, `Issues`).
- `New-RunContext`, an advanced function (`[CmdletBinding()]`) that validates inputs and
  applies defaults matching today's CLI behavior.
- A JSON serialize/rehydrate path so the context can cross a child-process boundary as plain
  data (SPEC §4.1: "serializes `$ctx` to JSON and rehydrates it (no live objects)"). This
  ticket must not add any secret value to the serialized shape.
- Dot-source the new file from `M365-Assess.psm1` beside the other `Common/` helpers.

## Acceptance

- [ ] `RunContext` exposes every member group in SPEC §4.1; a Pester test asserts the fields.
- [ ] `New-RunContext` builds a context from tenant/auth/scope/output inputs and is covered by
      a test that fails without the function.
- [ ] Round-trip JSON serialize + rehydrate is covered by a test.
- [ ] `RunContext` introduces no `$global:`/`$script:` state of its own.
- [ ] `M365-Assess.psm1` dot-sources the new file and `Import-Module` still loads the module.
- [ ] No file outside `scope` is modified.
