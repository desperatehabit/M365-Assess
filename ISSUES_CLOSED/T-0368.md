# T-0368 — CveException persistence, CRUD, expiry, and re-surface

## Report

EPIC-019 SPEC.md §5 defines `CveException` (`id`, `tenantId`, `cve`, `scope`, `reason`,
`expiresOn`, `createdBy`) as **expiring**, and §4.3 requires an expired exception to re-surface
the CVE and raise an alert (EPIC-029). §6 fixes
`GET`/`POST`/`PATCH`/`DELETE /v1/tenants/{id}/defender/cve-exceptions`. §11.3 is resolved to a
`scope` discriminator of `all` | `device` | `software`, defaulting to `all` (CVE-wide) with
optional device or software narrowing. §9 warns of exception creep, mitigated by mandatory expiry.

Deliver migration `0047_cve_exceptions.sql`, a `cve-exceptions.ts` repository (tenant-scoped,
expiry-aware) enforcing mandatory `expiresOn`, and CRUD routes behind RBAC `defender.write`.
Provide an expiry evaluation that reports lapsed exceptions so the TVM/CVE read path re-surfaces
the CVE and the EPIC-029 alert hook can fire. Exceptions are portal-local records, never tenant
writes; each write is audited.

## Acceptance

- [ ] A migration creates `CveException` with a mandatory `expiresOn`; CRUD round-trips the §5 fields.
- [ ] `scope` accepts `all`/`device`/`software` and validates the referenced device/software.
- [ ] An expired exception no longer suppresses the CVE; the CVE re-surfaces and the alert hook can fire.
- [ ] Tests cover repository, routes, and expiry re-surface and fail without them.
- [ ] No file outside `scope` is modified.
