# T-0832 — Stream run progress instead of buffering it

## Report

`GET /v1/runs/:runId/events` (T-0044) streams Server-Sent Events when its request context carries
the Node response (`res`), and otherwise collects events until the run ends and returns them in one
body. `buildServer` never passes `res`, and a handler that wrote to it would then have its returned
body sent a second time. T-0821 therefore mounts the route with a 25-second timeout
(`RUN_EVENTS_TIMEOUT_MS`): clients receive progress in batches and reconnect, rather than live.

Give the server a way for a route to take over the response (for example a `stream` result, or a
`res` on the context plus a "handled" marker the server honours), use it in the events route, and
drop the timeout. Client disconnects must unsubscribe from the hub.

## Acceptance

- [ ] Progress events reach a connected client as they are published, not at run end or timeout.
- [ ] The server sends nothing further for a route that handled the response itself.
- [ ] Closing the connection unsubscribes from the hub (test with an aborted request).
