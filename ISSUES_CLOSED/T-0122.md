# T-0122 — Schedule storage and repository

## Report

EPIC-007 SPEC.md §5 defines the `Schedule` entity with system timers marked `isSystem: true`.
§9 risk "system-timer editability" is mitigated by making `isSystem` rows read-only in the UI
**and API**; §1 splits code-deployed system timers from operator-created user tasks. §4.1 says
system timers live in code (`CIPPTimers.json` analogue) while user tasks live in the
`ScheduledTasks` table.

Deliver:

- A numbered, forward-only migration (`0004_schedules.sql`) for the `ScheduledTasks` table with
  `createdAt`/`updatedAt` and soft delete (`03-database.md` §5).
- `portal/db/src/schedule-repository.ts`: CRUD for user tasks; **rejects update/delete of
  `isSystem` rows at the repository layer**, not just in the UI; write of an `AuditEvent` on
  mutation.
- Tests for user-task CRUD, `isSystem` write rejection, and audit emission.

## Acceptance

- [ ] User schedules create, read, update, and soft-delete.
- [ ] Attempting to update or delete an `isSystem` row fails at the repository layer.
- [ ] Mutations write audit events.
- [ ] A test covers the change and fails without it.
- [ ] No file outside `scope` is modified.
