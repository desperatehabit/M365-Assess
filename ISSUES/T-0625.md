# T-0625 — Graph webhook subscription lifecycle, renewal, and notification dispatch

## Report

EPIC-032 SPEC.md §3.5 and §4.3 fix the webhook lifecycle: the portal subscribes to Graph change
notifications for required resources (users, groups, policies) per tenant; subscriptions renew
before expiry via a scheduled job, and failures raise alerts (EPIC-029); incoming notifications
are validated, matched to rules, and dispatched to alerts/caches. §6 exposes
`GET`/`POST`/`DELETE /v1/tenants/{id}/webhooks`, `POST /v1/tenants/{id}/webhooks/{id}/renew`,
with row actions `Renew`, `Recreate`, `Delete`, `Test`. Subscription management needs Graph
`Subscription.ReadWrite.All` app-only (SPEC §7). Resolved §11.2 **defers content-bundle
processing**: encrypted change payloads are acknowledged and stored by reference only in v1.

Build the `Manage-WebhookSubscription.ps1` worker job + `manage-webhooks.ps1` entrypoint (create,
renew, recreate, delete, test) and the BFF routes, including the unauthenticated notification
receiver `webhook-notify.ts` that validates the `clientState`, matches the resource, and
dispatches. Renewal is triggered by an EPIC-007 scheduled timer (T-0123, prose) that calls the
renew path; failures write an alert (EPIC-029, prose). Subscription changes write an
`AuditEvent`. Extend `portal.v1.yaml`.

## Acceptance

- [ ] List, create, renew, recreate, delete, and test all work; expiry is surfaced with an alert
      when a renewal fails.
- [ ] The notification receiver rejects an invalid `clientState` and dispatches a valid
      notification; an encrypted content payload is stored by reference only (content-bundle
      processing deferred).
- [ ] Subscription changes write an `AuditEvent`.
- [ ] A test covers the change and fails without it.
- [ ] No file outside `scope` is modified.
