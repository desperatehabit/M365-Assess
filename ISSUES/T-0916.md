# T-0916 — In-portal onboarding needs someone at the BFF machine's desktop

## Report

Onboarding signs in as an admin three times (Graph twice, Exchange Online once). Since T-0914
this works on Windows by opening a PowerShell window on the BFF machine, where Windows shows the
sign-in prompts. That holds for local development, where the operator sits at that machine. A
deployed BFF (a server, a container, a service account) has no interactive desktop, so the
prompts would appear to nobody, and the job waits until its 30-minute timeout. Off Windows, the
browser fallback has the same problem.

## Fix direction

Use the device-code flow for the admin sign-ins (`Connect-MgGraph -UseDeviceCode`,
`Connect-ExchangeOnline -Device`) when there is no interactive desktop, and relay each code to
the wizard (job progress event, displayed with the verification URL) so the operator signs in
from their own browser. Keep the sign-in window for local Windows use.

## Acceptance

- [ ] Onboarding completes from a BFF with no interactive desktop.
      Implemented end to end, but not proven yet: it needs a deployed headless BFF and a real
      tenant sign-in. Unit/route/component tests cover detection, the device-code parameters,
      the relay payload, and the wizard rendering.
- [x] The wizard shows each device code and URL while the job waits for it.
- [x] No file outside `scope` is modified.

## Fix

### Design

- **Desktop detection** (`Test-InteractiveDesktop` in `Invoke-TenantOnboarding.ps1`) is positive:
  a desktop exists only on Windows, in an interactive process, outside session 0 (services).
  `-Headless` or `M365_PORTAL_HEADLESS=1` force the device-code path. A hidden worker on a local
  Windows desktop still uses the existing T-0914 sign-in window, because that window is what
  carries the WAM prompt; headless mode is for machines with no desktop to draw on at all.
- **Graph capture**: `Connect-MgGraph -UseDeviceCode` writes
  `To sign in, use a web browser to open the page <url> and enter the code <code> to authenticate.`
  to its **output stream**. `Connect-M365AssessGraphSession` pipes the cmdlet through
  `ForEach-Object`, parses that line, and relays the code and URL while the cmdlet waits. This is
  the supported stream capture; Microsoft.Graph.Authentication 2.41.2 has no device-code callback
  parameter.
- **Exchange Online capture**: ExchangeOnlineManagement 3.7.2 `-Device` has no callback and
  writes the prompt only to the process console, which a PowerShell pipeline cannot read. The
  supported equivalent is used: `Get-M365DeviceCodeToken` runs the device-code flow in the MSAL
  library the module already ships (a small C# helper queues the code so the MSAL worker thread
  never has to invoke PowerShell), and `Connect-ExchangeOnline -AccessToken` completes the
  sign-in with the documented non-interactive parameter.
- **Relay**: the consent cmdlet takes `-SignInProgressCallback`, invoked with
  `Kind = device-code | sign-in-complete` plus `Stage` (`graph-bootstrap`, `graph-permissions`,
  `graph-operator`, `exchange-online`), `Provider`, `Code`, `VerificationUrl`, `ExpiresOn`.
  `Get-OnboardingSignInRelay` stamps `schemaVersion: v1`, a monotonic `sequence` and `at`, and
  writes one compact JSON line to the worker's stdout (or a test channel).
- **BFF progress channel**: `runFeatureWorker` gains `onProgressLine`, which forwards complete
  stdout lines while still collecting the final result. `createOnboardRunner` parses
  onboarding events from those lines, forwards them to the sink the route passes, and now pins
  the onboarding job to the 30-minute supervisor ceiling (it previously inherited the 5-minute
  feature-worker default). `onboard.ts` keeps one in-memory channel per client-supplied
  `progressId`, assigns the authoritative sequence, and serves
  `GET /v1/tenants/:id/onboard/progress/:progressId?since=N` (same admin permission and tenant
  scope as the POST). Starting a new onboarding for a tenant marks older channels `done`, and
  channels are pruned after 30 minutes idle. A `worker.timeout` becomes
  `onboard.timeout` / HTTP 504 with an operator-facing message.
- **Wizard**: generates a `progressId`, sends it with the POST, and polls the progress route while
  the POST waits. Only the latest pending code is shown, in a prominent panel with the provider,
  sign-in step, copy action, verification link and expiry; a newer code supersedes the previous
  one, a `sign-in-complete` event clears it, and an expired `expiresAt` shows an expired notice.
  Polling and device-code state are cleared when the submit finishes or fails.
- **Timeouts/messages**: each device-code wait defaults to 600s
  (`-DeviceCodeTimeoutSeconds`). Expired or abandoned codes throw
  `onboard.device_code_expired` / `onboard.device_code_timeout`, the Exchange connection step
  rethrows them instead of silently skipping RBAC, and the BFF's 30-minute job timeout reports
  `onboard.timeout`.

### Not met / uncertain

- Acceptance box 1 is unticked: there is no deployed headless BFF to prove a real sign-in
  end-to-end. The Graph prompt regex depends on the module's current wording
  ("open the page … and enter the code …"); a future wording change loses the relay (the job
  then waits and times out with `onboard.device_code_timeout`, and the raw prompt is only
  logged at verbose level).
- The relay is a per-job polling channel in `onboard.ts`, not the assessment-run SSE hub:
  onboarding is a synchronous feature worker with no Run row, and creating one was outside this
  ticket's scope. It uses the same v1 progress-event shape and the wizard's poll interval.
- `portal/contracts/openapi/portal.v1.yaml` was not regenerated for the new GET progress path;
  it is outside this ticket's scope and `openapi.test.ts` / `permissions.test.ts` pass without it.
