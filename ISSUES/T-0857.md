# T-0857 — Mount and wire EPIC-027 Sharing & Permissions routes

## Report

The EPIC-027 factories (`createSharingReportRoute`, `createSharingPermissionsRoute`,
`createExternalUsersRoutes`, `createSharingLinksRemoveRoutes`) exist under `portal/bff/src/routes/`
and are tested, but `portal/bff/src/app.ts` imports none of them and there is no adapter under
`portal/bff/src/adapters/`, so the endpoints 404. Workers (`get-sharing-report.ps1`,
`get-permissions-report.ps1`, `get-external-users.ps1`, `remove-sharing-links.ps1`) and migration
`0035_sharing_link_removal.sql` exist, and the UI (`SharingTable`, `PermissionsTable`,
`ExternalUsersTable`, `RemoveLinksDialog`, `RemovalPlanPreview`, `RiskyLinksView`) is present.

`portal/bff/src/routes/sharing-links-remove.ts:321` hard-fails with 501
(`SHARING_LINKS_UNAVAILABLE`, "not wired for this tenant") whenever the removal provider is absent,
so bulk removal cannot be exercised until the adapter is wired.

## Acceptance

- [x] Every EPIC-027 SPEC §6 endpoint returns a non-404 response from a running BFF.
- [x] Sharing report, permissions, external users, and link removal run their real workers.
- [x] Bulk link removal no longer returns 501 once the provider is configured.
- [x] No file outside `scope` is modified.

## Fix

`createSharingProviders` binds the four worker-backed seams to their existing
entrypoints. Every call carries the tenant credential block, so the BFF never
reaches Graph itself:

- `get-sharing-report.ps1` receives the flat report job (link type, permissions,
  site, created-after, anonymous-only, top, cursor) and returns the filtered page.
- `get-permissions-report.ps1` receives role, principal type, and pagination.
- `get-external-users.ps1` receives the T-0007 envelope's `payload` for the list
  (`search`) and the drill-through (`externalUserId`).
- `remove-sharing-links.ps1` runs one link per call in `Apply` mode with
  `confirmCount: 1` and maps the worker's per-link result to the route's
  removed/failed outcome.

`createApp` mounts all four route groups behind `resolveCaller`, the shared
authorizer, and the audit sink. The removal route now receives both its provider
and the LinkRemovalJob store (the shared repository over migration 0035), so an
apply creates and settles a job instead of returning `SHARING_LINKS_UNAVAILABLE`
(501); every attempt is audited. All endpoints are registered in the EPIC-038
permission registry, published through their OpenAPI fragments, and the
checked-in contract is regenerated.
