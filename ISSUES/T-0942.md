# T-0942 - Manage portal write access for an already-onboarded tenant

## Report

T-0917 provisions the opt-in `M365-Assess-Operator` app during **new-tenant
onboarding** and stores its credential with `purpose = "operator"`. An existing
tenant has no portal way to see whether write access is enabled, which groups
were granted, add it, change it, or disable it. The only paths are the
`Grant-M365AssessConsent` cmdlet or the onboarding API run by hand.

Re-running the cmdlet is additive: selecting fewer groups does not remove
previously granted app roles, directory roles or EXO role-group membership.
Disabling write access is not exposed at all, and the tenant detail Credential
tab shows only the reader credential.

## Fix direction

- **API**
  - `GET /v1/tenants/{id}/credentials` returns every credential for the tenant
    (reader and operator) with `purpose` and `permissionGroups`.
  - `DELETE /v1/tenants/{id}/credential?purpose=operator` removes the operator
    credential row and records an audit event. The reader row cannot be deleted
    through this path. The Entra app and its grants are left in place
    (operator decision, 2026-11-22).
  - `POST /v1/tenants/{id}/onboard` accepts `replaceWriteGroups`. When true, the
    worker reconciles the operator app's managed grants to the selected groups:
    add the selected ones and remove the unselected ones from the operator app
    only. The reader app is never touched.
- **Storage:** a forward-only migration adds `permissionGroups` to
  `tenant_credentials`; the onboarding route writes the granted groups to the
  operator row.
- **Cmdlet:** `Grant-M365AssessConsent -ReplaceWriteGroups` removes managed
  operator AppRole assignments, directory-role memberships and EXO role-group
  memberships that are no longer selected. It never removes grants outside the
  T-0917 matrix and never changes the reader app.
- **UI:** tenant detail gets an **Access** tab:
  - Reader card (client id, auth method, thumbprint, state).
  - Write access card: enabled/disabled, operator client id, groups, last updated.
  - Grant / Change groups dialog (Admin UPN, group selection, dangerous
    confirmation, device-code progress) and Disable action with confirmation.
  - PFX credentials that cannot supply a thumbprint get a copyable CLI fallback
    instead of a broken submit.

### Backend (2026-11-22)

- **Storage:** forward-only `0134_credential_permission_groups.sql` adds
  `tenant_credentials.permissionGroups` (JSON text, NULL for reader rows).
  `TenantCredential.permissionGroups` maps to `string[] | null`;
  `SqliteRepository.deleteTenantCredential(tenantId, purpose)` deletes exactly one
  purpose's row and leaves the other. Re-onboarding now updates the existing
  reader/operator row id instead of appending a duplicate.
- **Credential API:** `GET /v1/tenants/{id}/credentials` returns
  `{ items: CredentialView[] }` with `purpose` and `permissionGroups`;
  `GET /v1/tenants/{id}/credential` still returns the reader by default.
  `DELETE /v1/tenants/{id}/credential?purpose=operator` returns 204, writes a
  `tenant.credential.delete` audit event, returns 400 for any other purpose and
  404 when the operator row is absent. It never deletes secret material or the
  Entra app/grants. `CredentialStoreRow` exposes `listCredentials` and
  `deleteCredential`; `createCredentialRowStore` maps them to the repository.
- **Onboarding route:** parses `replaceWriteGroups`, forwards it to the worker,
  and writes the operator row's `permissionGroups` from
  `workerResult.writePermissionGroups`, falling back to
  `input.writePermissionGroups`. The audit event records the same groups.
- **Worker:** `Invoke-TenantOnboarding` passes `-ReplaceWriteGroups` to
  `Grant-M365AssessConsent`; `onboard-tenant.ps1` reads `replaceWriteGroups` from
  the job envelope.
- **Cmdlet reconciliation:** `Grant-M365AssessConsent -ReplaceWriteGroups` (which
  requires `-IncludeWritePermissions`) adds the selected grants, then removes
  only T-0917 matrix-owned operator grants that are no longer selected:
  - Graph app roles whose permission is in `$script:OperatorWriteGroups`
    (unrelated assignments are skipped);
  - `Exchange.ManageAsApp` / `Organization.Read.All` / `MailboxSettings.Read`
    and `Purview.ApplicationAccess` app roles when `exchange` is not selected;
  - directory roles from `$script:OperatorDirectoryRoleTemplates`;
  - EXO role groups from the matrix (the delegated Exchange session opens even
    when no EXO group is selected).
  Removals append `Status = 'Removed'` entries, are counted in the step summary,
  and are planned under `-WhatIf`. The reader app is a different service
  principal and is never read or changed.
- **OpenAPI:** the credential and onboarding fragments are registered in
  `ROUTE_OPENAPI_FRAGMENTS`, so `portal.v1.yaml` carries the list/delete
  operations, `TenantCredentialView`/`TenantCredentialList` schemas, the delete
  `purpose` enum, and the `replaceWriteGroups` request field. The onboarding
  fragment paths use the repo's no-`/v1` OpenAPI convention.
- **Verification:** DB `46 files / 312 tests`, BFF `385 files / 4509 tests`
  (single worker; the shared host lacks commit memory for the default parallel
  run), BFF/DB `tsc` and builds clean, Pester
  `Grant-M365AssessConsent.Tests.ps1` 37 passed and
  `Invoke-TenantOnboarding.Tests.ps1` 39 passed / 1 platform skip.

Remaining: live UI walk on an onboarded tenant (the web changes are owned by the
parallel web work) and the T-0941 live runbook verification.

## Live finding (2026-11-23)

The first live grant on an onboarded tenant reached the operator app creation and
failed at the Exchange Online role-group step:

```
Exchange Administrator (Failed: ||The operation couldn't be performed because
object 'Exchange Administrator' couldn't be found on
'DM8PR06A07DC003.NAMPR06A007.PROD.OUTLOOK.COM'.)
```

Two fixes:

- `Test-ExoTransientObjectError` now recognises the "couldn't be found" and
  "couldn't be performed because object" DC-propagation wordings, so the existing
  retry loop actually retries the role-group add (it previously matched only
  "could not be found"/"not found").
- When the retries are exhausted but the operator app already has the Entra
  **Exchange Administrator** directory role (the app-only authorization surface),
  the EXO role-group entry is recorded as `Warning` instead of `Failed`, so
  onboarding completes and stores the operator credential. The Access panel shows
  a warning naming the role group and asks the operator to retry later if Exchange
  cmdlets fail. The step stays fatal when the Entra role is missing.

The failed attempt left the operator app provisioned but no stored credential;
re-running **Add write access** after the BFF restart resumes and completes it.

### Second live finding (2026-11-23): partner-managed role group

The retry then reached the tenant’s `ExchangeServiceAdmins_102400532` role
group, which carries capability `Partner_Managed`:

```
The operation ... failed because it's out of the current user's write scope.
... may not be performed on the management role group
'ExchangeServiceAdmins_102400532' with capability 'Partner_Managed'. Membership
of a partner managed role group can't be changed.
```

This is permanent, not replication: the delegated admin cannot change that role
group. It does not block write access because the operator app already has the
Entra **Exchange Administrator** directory role, which is the app-only
authorization surface.

- `Test-ExoPartnerManagedRoleGroupError` classifies `Partner_Managed`,
  `partner managed role group`, and `out of the current user's write scope`.
- The operator EXO step does not retry a partner-managed refusal. When the Entra
  role is assigned it records `Warning`, so onboarding completes and stores the
  operator credential; the Access panel warns with “(partner-managed)”.
- When the Entra role is missing, the step stays `Failed` with an actionable
  message: assign the Entra role or use the partner’s GDAP role, then retry.
- Tests cover both cases; the EXO suite is still gated on the module for CI.
