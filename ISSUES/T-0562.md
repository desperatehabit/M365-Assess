# T-0562 — Curated v1 built-in alert catalog and alert-rule CRUD API

## Report

EPIC-029 SPEC.md §2 US-1 and §3.1 define the Alert Configuration table (Name · Source · Severity ·
Scope · Channels · State · Last fired) with row actions `Edit`, `Clone & edit`, `Enable/Disable`,
`Delete`, `Test`; §6 fixes `GET`/`POST`/`PATCH`/`DELETE /v1/alert-rules` and the toggle operation.
§11.1 is resolved to adopt a **curated v1 built-in subset** with the full ~70 set later, so this
ticket must define that subset in code.

Deliver a `builtin-catalog.ts` enumerating the v1 built-ins (credential expiry approaching; run
failed; run partial; new drift deviation; standards regression; connector/transport change;
Conditional Access policy change; new privileged-role assignment; mailbox forwarding enabled;
secure-score drop; delivery-channel failure meta-alert; incident spike) each with source, default
severity, scope, and default channels. Add the rule CRUD + enable/disable routes behind RBAC
`alerts.read`/`alerts.write` (full RBAC is EPIC-038; this epic uses the EPIC-001 T-0013 seam), and
extend `portal.v1.yaml`. Built-ins are seeded as rules the operator can enable; `Test` delivery is
T-0564. No tenant writes.

## Acceptance

- [ ] `GET /v1/alert-rules` returns built-in and custom rules with the §3.1 columns.
- [ ] `POST`/`PATCH`/`DELETE` create, edit, and delete rules with scope and channel assignment.
- [ ] The built-in catalog enumerates the curated v1 subset and marks each as built-in vs custom.
- [ ] Enable/disable toggles a rule and writes an audit event.
- [ ] Tests cover the catalog and routes and fail without them.
- [ ] No file outside `scope` is modified.
