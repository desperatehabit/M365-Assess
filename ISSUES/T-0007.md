# T-0007 — Portal workspace, versioned job/result envelope, and OpenAPI skeleton

## Report

ADR-0014 fixes the runtime: a thin BFF owns HTTP concerns and every domain operation crosses to
a PowerShell worker over a **versioned job envelope and matching result envelope** as plain
JSON. EPIC-001 SPEC.md §4.2 says `result.json` **is** the result envelope, and the layout table
puts envelopes, progress events, OpenAPI, and generated types in `portal/contracts/`.

Deliver:

- `portal/package.json` as the npm-workspaces root (`contracts`, `bff`, `web`, `db`), separate
  from the existing report build tooling at the repo root.
- `JobEnvelope`, `ResultEnvelope`, and progress-event types with an explicit `schemaVersion`,
  request/correlation ids, tenant id, run id, and job type. Envelopes carry **references, not
  secrets or blobs** (ADR-0014 failure modes).
- An initial OpenAPI 3.1 document (`portal.v1.yaml`) that later route tickets extend; structured
  error and cursor-pagination schemas live here.
- Unit tests that round-trip both envelopes and reject a mismatched `schemaVersion`.

## Acceptance

- [ ] `JobEnvelope`/`ResultEnvelope`/event types exist with a version discriminator.
- [ ] A test round-trips both envelopes and fails on an unknown `schemaVersion`.
- [ ] The OpenAPI document parses and defines the structured error + pagination schemas.
- [ ] No M365 SDK or domain/check logic is introduced.
- [ ] No file outside `scope` is modified.
