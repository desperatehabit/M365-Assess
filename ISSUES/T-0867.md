# T-0867 — Mount EPIC-037 Settings, Branding & Preferences routes

## Report

The EPIC-037 factories (`createSettingsRoutes` at `portal/bff/src/routes/settings.ts:267`,
`createBrandingRoutes` at `branding.ts:218`, `createFeatureFlagRoutes` at `feature-flags.ts:126`,
`createPreferencesRoutes` at `preferences.ts:114`, `createLogbookRoutes` at `logbook.ts:240`,
`createDiagnosticsRoutes` at `diagnostics.ts:142`) exist and are tested, but
`portal/bff/src/app.ts` imports none of them and there are no adapters bridging the repositories in
`portal/db/src/` to the route stores, so the endpoints 404. `diagnostics.ts` also replaces the
EPIC-001 stub with the full `GET /v1/diagnostics` report, but it is not mounted.

Pages exist (`app/settings`, `app/settings/branding`, `app/settings/features`,
`app/settings/notifications`, `app/preferences`, `app/advanced/diagnostics`, `app/logbook`); only
`/diagnostics` is linked in the nav.

## Acceptance

- [x] Every EPIC-037 SPEC §6 endpoint returns a non-404 response from a running BFF.
- [x] Settings, branding, feature flags, preferences, logbook, and diagnostics persist and serve live data.
- [x] `GET /v1/diagnostics` returns the full report rather than 404.
- [x] No file outside `scope` is modified.

## Fix

`createSettingsStores` bridges the route seams to the db repositories: settings
read through `listSettings` and write through a new atomic `applySettings` (one
transaction, one audit row per key, so a rejected batch leaves nothing written);
branding adds the BFF schema version to the db row and strips it on save; feature
flags, preferences (with typed defaults on first read), and the logbook's
identity/action/outcome projection share the same connection.

`createApp` mounts all six route groups. Branding reuses the artifact root for
asset upload/download and audits only the asset write, because the repository
already audits the config save. Logbook and diagnostics are the read-only admin
surface; their `CIPP.Admin.*` scope constants became concrete
`CIPP.Admin.Logbook` / `CIPP.Admin.Diagnostics` permissions so the EPIC-038
registry stays taxonomy-valid. The diagnostics report is the full EPIC-001 health
report plus cache status and the merged system-timer state. All endpoints are
registered, published through their OpenAPI fragments, and the checked-in
contract is regenerated.
