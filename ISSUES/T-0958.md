# T-0958 — The exchange write group assigns Security Operator instead of a Purview role

## Report

- `$script:OperatorDirectoryRoleTemplates` in `PermissionDefinitions.ps1` mapped
  `'eDiscovery Manager'` to template id `5f2222b1-57c3-48ba-8ad5-d4759f1fde6f`. In Entra that id
  is **Security Operator**. eDiscovery Manager is a Purview role group, not an Entra directory role,
  so no template id for it exists.
- Selecting the Exchange & Purview write group therefore gave the operator app Security Operator, a
  role nobody chose, and no Purview role.
- Observed on the test tenant after a portal write-access update with all five groups: the operator
  app held Exchange Administrator, Security Operator and Teams Administrator. Its app-only IPPS
  session had no compliance write cmdlets (`New-DlpCompliancePolicy`,
  `Set-SupervisoryReviewPolicyV2`), so DLP, retention, labeling and communication compliance
  remediation could not run. Exchange Online writes worked.

## Fix

- The exchange group assigns **Compliance Administrator** (`17315797-102d-40b4-93e0-432062caca18`)
  in place of the mislabelled entry (maintainer decision, 2026-11-24).
- `$script:OperatorRetiredDirectoryRoleTemplates` lists Security Operator. A `-ReplaceWriteGroups`
  run removes it from the operator app whatever is selected, so tenants that were set up with the
  bad mapping are cleaned up by the portal's "change write access" flow.

## Acceptance

- [x] The exchange group's directory roles map to Exchange Administrator, Compliance
      Administrator and Teams Administrator template ids; the Security Operator id is not used.
- [x] A `-ReplaceWriteGroups` run removes Security Operator from the operator app.
- [x] Tests cover both and fail without the change.
- [ ] Live: after re-running write access from the portal, the operator app holds Compliance
      Administrator and not Security Operator, and its IPPS session exposes
      `New-DlpCompliancePolicy`.
