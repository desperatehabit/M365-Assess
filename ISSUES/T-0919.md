# T-0919 — Each run appears twice in the Runs list, and only one copy has findings

## Report

Starting one assessment adds two rows to **Assessments > Runs**. Only one of them has data or
findings. The other looks like an empty copy of the same run.

## Likely cause

`runs-create.ts` always creates a **parent** run plus one **child** run per tenant, even when
only one tenant is targeted. The parent takes the first target's `tenantId` (line 163), so it
looks the same as its child. Jobs, results and findings attach to the child.

`GET /v1/runs` (`runs-list.ts`) returns parents and children as one flat list. The Runs page
does not nest the children. `RunsTable` has code for `run.children` (the "N tenants" badge),
but nothing fills `children`. Each single-tenant run therefore shows as two rows: the empty
parent and the child that has the findings.

**Confirmed against the live database (2026-11-19).**
- The walk's run has two rows. The child holds all 167 findings, the summary counts and the
  artifact path.
- The parent has `parentRunId: null`, `summaryCounts: null` and `artifactPath: null`, and the
  child's `tenantId`.
- `runs-list.ts:140` filters by `parentRunId` only when the query asks for it.
- The run detail and results routes do roll up the children, but the list row for the parent
  has no counts, so it looks empty.

## Fix direction

- Return only top-level runs by default and nest children under their parent (or have the page
  group them by `parentRunId`). A single-tenant run shows as one row that opens straight to
  the child's results.
- Or create no parent for a single-tenant run. That changes the run model, so check
  EPIC-003 SPEC §3.1 first.
- A parent run's status, counts and findings should roll up from its children, so the parent
  row is never empty.

## Acceptance

- [x] Starting a single-tenant run adds exactly one row to the Runs list.
- [x] A multi-tenant run shows one parent row that expands to its per-tenant children.
- [x] Opening either row shows the findings.
- [x] No file outside `scope` is modified.

## Fix

**Approach: collapsed at the list/presentation layer; the run model is unchanged.**
The stored parent + per-tenant child rows from EPIC-003 SPEC §11.1 (and the §3.1 table)
stay exactly as they are. `GET /v1/runs` now returns *logical* rows, and `RunsTable`
renders the multi-tenant row as one row that expands to its children.

- `portal/bff/src/routes/runs-list.ts`
  - A parent with exactly **one** child is represented by that child's row, so a
    single-tenant run appears once with the child's ID, counts, timestamps, status and
    artifact path. The empty parent row is not listed.
  - A parent with **more than one** child stays one row. Its `children` array carries the
    per-tenant runs, and `status` (`rollupRunStatus`), `startedAt`/`finishedAt`/`durationMs`,
    `summaryCounts` (summed) and `progress` are rolled up from the children, so the parent
    row is never empty. `tenantDisplayName` is cleared (the row spans tenants, see T-0918).
  - A child whose parent is not in the result set (RBAC scope or tenant filter) is listed
    on its own, so no row is lost.
  - Row filters (status, trigger, tenant, section, date) match the row or any of its
    children. `?parentRunId=` keeps the previous flat child listing.
  - Pagination `total` is the number of logical rows.
- `portal/web/src/components/RunsTable.tsx`
  - The "N tenants" badge is now an expand/collapse button. Expanded rows render one
    child row per tenant (name + ID, status, counts, started, duration) with a `View`
    action that opens that child run.
  - Card view lists the children when expanded.
- Findings/links: a collapsed single-tenant row opens `/runs/{childId}`, whose existing
  detail/results routes hold the findings; a multi-tenant parent opens `/runs/{parentId}`,
  whose existing detail/results routes aggregate its children. No route or link changed.
- `runs-create.ts` and `web/src/app/runs/page.tsx` were inspected and needed no change:
  creation keeps one parent + one child per tenant, and the page renders whatever the list
  returns.
