# T-0017 — Make migration version numbers unique and loudly guarded

## Report

EPIC-001 SPEC.md §5 and ADR-0015 require numbered, forward-only migrations with a startup gate
on `SchemaVersion`. `runMigrations` in `portal/db/src/sqlite-repository.ts` keys the applied
set by version number only, so two files sharing a version silently shadow each other: the
second file with an already-applied version is never executed. The tree currently ships five
such duplicates (`0002_rbac.sql` vs `0002_tenants.sql`; `0003_ca_templates.sql` vs
`0003_intune_templates.sql` vs `0003_offboarding.sql`), so on a fresh database an arbitrary
one of each group wins depending on directory order.

Deliver:

- A load-time guard: `loadMigrations` (or the startup path) fails fast when two migration
  files parse to the same version.
- Renumber the five duplicates to free, strictly increasing numbers above the current
  on-disk maximum, preserving their original relative order. Keep the descriptive suffixes.
- A test that loads the real migrations directory and asserts every version is unique.
- A test that a database which already recorded the old duplicate versions still migrates
  cleanly (no re-application, no `CREATE TABLE` failure on existing tables).

## Acceptance

- [ ] Duplicate version numbers are rejected at load with a clear error naming both files.
- [ ] Every migration file on disk has a unique version, ordered consistently with its content
      dependencies.
- [ ] A database carrying the legacy duplicate version rows migrates without error.
- [ ] `portal/db/src/storage.test.ts` covers the above and fails without the change.
- [ ] No file outside `scope` is modified.
