# T-0947 — An onboarded tenant is named after the app registration

## Report

- The run detail header and tenant lists show the test tenant as `M365-Assess-Reader`, which is
  the default name of the reader app registration, not the organization.
- `portal/bff/src/routes/onboard.ts` (around line 439) builds the tenant row with
  `displayName: input.displayName ?? workerResult.appDisplayName ?? existing?.displayName ?? null`.
  When the operator leaves the name blank, the app's display name becomes the tenant's name.
- `Invoke-TenantOnboarding.ps1` returns `appDisplayName` but not the organization's display name
  or verified domains, so the route has nothing better to fall back to.

## Fix direction

- Have the onboarding worker read `GET /organization` and return the organization
  `displayName`, the default domain and the initial (`*.onmicrosoft.com`) domain.
- Fall back in this order: operator input, organization name, existing row, tenant ID. Never use
  the app registration's name.
- Fill `defaultDomain` / `initialDomain` from the same response when the operator did not.
- Repair existing rows: re-onboarding (or a one-off backfill) replaces a display name that equals
  the app's name.

## Acceptance

- [ ] Onboarding without a typed name stores the organization's display name and domains.
- [ ] No code path stores `appDisplayName` as the tenant's `displayName`.
- [ ] Tests cover the fallback order, and fail without the change.
