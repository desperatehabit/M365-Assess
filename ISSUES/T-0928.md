# T-0928 — Remediation jobs overwrite the assessment run's status and timestamps

## Report

The walk's run shows `startedAt` 14:22:48.548Z and `finishedAt` 14:22:49.501Z, a duration of
about 1 second. The assessment job actually ran from 13:19:57 to 13:21:34. The run's
timestamps equal the `createdAt` and `updatedAt` of a **remediation** job (`01795cc7`) to the
millisecond. The parent run inherited the same values through rollup.

## Cause

`portal/bff/src/sse/hub.ts:373-390` applies any job's running or terminal event to the run
named by `event.runId`. Remediation plan and apply jobs carry the assessment run's ID
(`buildRemediationEnvelope(..., runId, ...)`, `routes/remediation.ts:370` and `:454`), so their
lifecycle overwrites the assessment run's status and times.

**Risk:** a failed remediation marks the assessment run as failed, and a running remediation
flips a finished run back to `running`.

## Fix direction

- Update run status and timing only from the run's own assessment job(s), for example by
  checking `job.kind === "assessment"`.
- Remediation jobs update their plan or history record and keep `runId` as a link only.
- Add a regression test: a completed run, then a remediation job runs and fails, and the run
  stays `succeeded` with its original times.

## Acceptance

- [x] A remediation job's events never change the assessment run's status, `startedAt` or
      `finishedAt`.
- [x] The run duration in the portal matches the assessment job.
- [x] No file outside `scope` is modified.

## Fix

- `portal/bff/src/sse/hub.ts`
  - Added `ownsRunLifecycle(event)`: only `jobType === "assessment"` events may move the
    run. `updateStore` now returns before writing run or section state for any other job
    type, so remediation plan/apply/verify (and other linked job types) cannot change
    `status`, `startedAt`, `finishedAt` or run sections.
  - Run terminal tracking (`terminalRuns`, stream completion/close) is likewise limited
    to assessment events, so a remediation job's terminal event no longer closes the
    assessment run's progress stream or marks the run terminal.
  - Run-state change detection (`runStates`) is keyed off assessment events only, so a
    remediation event can no longer mask or force a run update.
- `portal/bff/src/routes/remediation.ts`
  - Documented in `buildRemediationEnvelope` that `runId` is a reference to the
    assessment run that produced the findings, not a claim on its status or timing; the
    envelope keeps `jobType: "remediation"` and its own output folder.
- Tests
  - `portal/bff/src/sse/hub.test.ts`: regression tests for a completed (succeeded) run
    followed by a failing remediation job (run keeps `succeeded` and its original
    `startedAt`/`finishedAt`), a running remediation not flipping a finished run back to
    `running` (and not writing run sections), and a standalone remediation terminal event
    not marking the run terminal. The fake store now models the stored run so the
    unchanged state is asserted directly.
  - `portal/bff/src/routes/remediation.test.ts`: integration test publishing the plan
    envelope's lifecycle through the hub, asserting the completed run receives no further
    updates.
- Verification
  - `cd portal/bff; npx vitest run src/sse/hub.test.ts src/routes/remediation.test.ts` —
    2 files, 24 tests passed.
  - `cd portal/bff; npx tsc -p tsconfig.json --noEmit` — clean.
