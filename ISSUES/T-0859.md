# T-0859 — Mount EPIC-029 alerting routes and persist alerting entities

## Report

The EPIC-029 factories (`createAlertRulesRoutes`, `createAlertRulesTestRoutes`,
`createAlertEventRoutes`, `createNotificationRoutes`) exist under `portal/bff/src/routes/` and are
tested against fake stores (`FakeStore` in the route tests), but `portal/bff/src/app.ts` imports none
of them and there is no adapter. Result: the endpoints 404 and the alerting entities have no
durable store.

Deeper gap (SPEC §5): migration `portal/db/migrations/0037_alerting.sql` defines `alert_rules`,
`alert_events`, `notification_configs`, and `webhook_rules`, but no repository in
`portal/db/src/` or `portal/bff/src/repository/` implements the route store interfaces
(`AlertRulesStore`, `AlertEventStore`, `NotificationConfigStore`, `WebhookRuleStore`). A repo-wide
search finds those interfaces implemented only by test fakes.

UI gap (SPEC §2 US-6, §3.5, §10): the alert configuration page
(`app/tenant-administration/alerts/page.tsx:285`) has only `config` and `snoozed` tabs and queries
`/v1/alert-events?state=snoozed`; there is no queue/history view of open and resolved events.

## Fix direction

Add SQLite repositories over migration 0037, an alerting adapter, and mount the four route groups;
then add the open/resolved alert history view.

## Acceptance

- [x] Every EPIC-029 SPEC §6 endpoint returns a non-404 response from a running BFF.
- [x] Alert rules, events, notification configs, and webhook rules persist through SQLite (no test-only store).
- [x] The alert queue/history view exists and shows open and resolved events.
- [x] No file outside `scope` is modified.

## Fix

Migration 0128 adds the columns the route contracts read but 0037 omitted: `alert_rules`
`tenantId`, `severity`, `scope`, `channels`, `builtIn`, and `alert_events.source`.
`SqliteAlertingRepository` implements all four entities: rule CRUD with a derived
`lastFiredAt`, event list/filter/pagination plus snooze and auto-return, notification
channel configs, and outbound webhook-rule upsert/delete. `webhook_rules` has no SPEC §6
endpoint, so it is persisted through the repository for the delivery pipeline rather than
a route.

`createAlertingStores` binds the four route stores, seeds the 12 built-in rules (disabled)
and the four notification channels on first read, exposes each rule's authored criteria to
the dry-run store, and decorates events with the owning rule's source for the queue view.
The dry-run evaluator reads each tenant's latest finished run findings; Graph log sources
arrive with the evaluation worker, so those rules report "No matching data" instead of a
fabricated match.

All ten endpoints are mounted in `createApp`, registered in the permission registry, and
published through the EPIC-029 OpenAPI fragments; `portal.v1.yaml` is regenerated. The
alert page gains an "Alert queue" tab that renders open and resolved events with state,
rule, source, tenant, severity, and fired time.
