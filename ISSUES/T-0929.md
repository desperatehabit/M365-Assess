# T-0929 — A run with failed sections reports `succeeded`, and the portal never shows its issues

## Report

The walk's run had two ERRORs in `_Assessment-Issues` (the EXO and Purview connection
failures, T-0926), and about 10 collectors did not run. `result.json` and the DB both say
`succeeded`. The run detail's Issues tab is empty.

## Cause

- The DB status column allows `partial`, but the BFF never writes it (see the comment in
  `adapters/runs.ts` around line 84).
- `RunsDetailStore.listRunIssues` is declared (`routes/runs-detail.ts:133`), but no store
  implements it. Issues fall back to `options` or `provenance`, which are empty, so the
  `_Assessment-Issues` log is never served.
- `run_sections` is empty for this run, so there is no per-section status to roll up either.

## Fix direction

- When a run's artifacts are ingested, parse `_Assessment-Issues` (and the per-collector
  status in the summary CSV) into run issues and `run_sections`.
- Set the run to `partial` when any requested section errored or was skipped for a reason
  other than the operator's own options.
- Show `partial` with a warning badge in the Runs list, and the issues on the Issues tab, with
  an issue count on the tab label.

## Acceptance

- [x] A run whose EXO connection fails ends as `partial`, not `succeeded`.
- [x] The Issues tab lists each ERROR and WARN from `_Assessment-Issues`.
- [x] `run_sections` holds each section's status.
- [x] No file outside `scope` is modified.

## Fix

- `portal/bff/src/adapters/runs.ts`
  - `withFindingsIngestion` now reads the run's `_Assessment-Issues*.log` and
    `_Assessment-Summary*.csv` artifacts (both optional; a malformed one cannot fail a
    run whose findings export parsed). `parseAssessmentIssues` reads
    `Export-IssueReport`'s block format (Severity/Section/Collector/Description/Error)
    and `parseAssessmentSummary` collapses the per-collector CSV (`#` comment header,
    Complete/Failed/Skipped) to one status per section.
  - Section rows are written to `run_sections` when the progress stream did not already
    create them (one row per section, `collector: null`).
  - The run becomes `partial` when any issue is ERROR, any section failed, or a section
    was skipped for a reason the operator did not choose. A skip caused by
    `-SkipPurview` (its error names Purview / Security & Compliance) is an operator
    choice and does not make the run partial.
  - The issue list and a `partial` marker are merged into `provenance`; the real store
    implements `listRunIssues(tenantId, runId)` from `provenance.issues`.
  - `updateRun` / `updateRunById` refuse to downgrade a `partial` run (provenance
    `partial: true`) back to `succeeded`, because the queue's terminal succeeded event
    is emitted after ingestion.
- `portal/bff/src/routes/runs-detail.ts` — both detail paths call `listRunIssues` and
  expose `issueCount` (single run and sum over visible children); the results route
  reuses the same helper.
- `portal/web/src/components/RunDetailTabs.tsx` — the status badge styles `partial` with
  the warn tokens; the Issues tab label uses the detail's issue count
  (`Math.max(issues.length, run.issueCount)`) and a partial run shows a warning banner
  above the issue list.
- `portal/web/src/components/RunsTable.tsx` — the existing `partial` badge used the
  undefined `--warning-*` tokens; it now uses the theme's `--warn-soft` / `--warn-text`
  / `--warn`. Expansion logic untouched.
