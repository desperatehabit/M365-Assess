# T-0905 — Ingest NinjaOne endpoint data into reports and the CMMC SSP

## Report

Endpoint and Windows configuration evidence will come from NinjaOne (formerly NinjaRMM) for
customers who want it (maintainer decision, 2026-11-05). M365-Assess has no endpoint
collector, so the 454 upstream CheckID `WIN-*` checks (filtered out by
`controls/sync-scope.json`) and the endpoint side of CMMC practices such as 3.3.7, 3.4.1,
3.4.2, 3.13.6, and 3.14.2 have no automated evidence today. They fall back to the SSP
questionnaire.

Pick one ingestion route, or support both:

- **API:** the portal pulls device inventory, patch and antivirus status, and script or
  custom-field results from the NinjaOne API per customer (credentials stored like tenant
  credentials), on a schedule or on demand.
- **Export/import:** a NinjaOne export is uploaded to the portal (or passed to
  `Invoke-M365Assessment`) and parsed.

Either way, results become findings keyed to registry check ids, so they appear in the report
and feed the SSP's automated evidence through the existing CMMC mappings. Configuration
checks that NinjaOne does not report natively can run as a NinjaOne script that writes to
custom fields. The HardeningKitty finding lists (MIT) are a starting point for that script;
see `docs/research/endpoint-network-collector-options.md`, including its CIS licensing
caution.

## Acceptance

- [ ] An ingestion route is chosen and documented (API, export/import, or both).
- [ ] NinjaOne data for a test customer produces findings with registry check ids, shown in
      the report and as automated evidence in the SSP.
- [ ] `controls/sync-scope.json` brings in the `WIN-*` checks that have a data source.
- [ ] Tests cover parsing and the mapping to check ids.
