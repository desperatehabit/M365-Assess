# T-0725 — Feature flag schema, repository, API, and enforcement seam

## Report

EPIC-037 SPEC.md §5 defines `FeatureFlag` (`key`, `enabled`, `scope`, `description`); §3.3 says
flags gate nav items and endpoints consistently; §6 defines `GET`/`PUT /v1/feature-flags`; §9 names
**feature-flag inconsistency** (UI shows a feature the API disables) as a risk mitigated by
enforcing flags at the API while nav reads the same source. §11.3 resolves granularity to **global
first, per-tenant later**.

Deliver migration `0112_feature_flags.sql` and repository get/upsert for flags at **global** scope
(a `tenant` scope value is reserved and rejected in v1), `routes/feature-flags.ts` for
`GET`/`PUT` (audited, `CIPP.AppSettings.*` seam), and `feature-flags/enforce.ts`, a single
server-side guard that nav and endpoint code both consult so the UI cannot show a disabled feature.
Update `portal.v1.yaml`.

## Acceptance

- [ ] `GET`/`PUT /v1/feature-flags` are implemented and match the OpenAPI document; changes are audited.
- [ ] An endpoint behind a disabled flag returns a structured "feature disabled" error; the same source drives nav.
- [ ] A `tenant`-scoped flag is rejected in v1 (deferred to per-tenant later).
- [ ] A test covers the enforcement seam and fails without it.
- [ ] No file outside `scope` is modified.
