# T-0902 — Implement the webhooks system timer (Graph subscription renewal)

## Report

T-0876 found that the `webhooks` system timer (`portal/bff/src/scheduler/system-timers.ts`)
names `Invoke-WebhookRenewal`, which no worker or runner implements. It used to be enqueued as a
`report` job that no runner could execute, so every tick threw 501. T-0876 marked it
`unavailableReason`, so it is now listed as disabled and skipped.

Implement renewal: for each tenant, list its Graph change-notification subscriptions and renew those close to expiry through `portal/workers/manage-webhooks.ps1` (`-Action renew`), recreating any that have lapsed. Record failures so EPIC-032 surfaces them.

Then remove `unavailableReason` from the timer so the tick runs it again.

## Acceptance

- [x] The behaviour described in the report is implemented and the timer runs on its cron.
- [x] A test covers the timer's run and fails without the fix.
- [x] No file outside `scope` is modified.

## Fix

Added the `maintenance` job type and a command-dispatched runner
(`portal/bff/src/scheduler/maintenance.ts`). The tick copies each system timer's `command`
into the job payload, and `createWebhookRenewalCommand` lists every included tenant's Graph
subscriptions through `manage-webhooks.ps1` (`action: list`), renews the ones expiring within
24 h, and recreates the lapsed ones. Failures are recorded as audit events through the BFF's
audit sink so EPIC-032 surfaces them; the job then finishes `failed`.

The timer registry also now persists last/next run in `system_timer_state` (migration 0127),
so a code-deployed timer runs on its cron instead of being due on every 60 s tick. The
`unavailableReason` mechanism stays for future timers but none set it today.
