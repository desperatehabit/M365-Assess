# T-0925 — Findings can't be remediated from the run screen; remediation is a separate page

## Report

The Runs and Remediation pages look like they should be one. A run already has the findings,
and its summary is useful, but the operator wants to remediate a finding straight from the
assessment run screen instead of going to a separate Remediation page.

## Current state

- **Run detail** (`RunDetailTabs.tsx`) has Summary, Progress, Findings, Artifacts and Issues
  tabs. Findings rows open nothing, because there is no finding drawer. The only route to
  remediation is a **Plan remediation** link (around line 943) to
  `/remediation?tenantId=…&runId=…`, which builds a plan on a separate page
  (`RemediationView`, EPIC-006 §3.2).
- The link is hidden on parent runs (`!(run.children && run.children.length > 0)`). With the
  duplicate rows from T-0919, the link appears on one of the two rows only.
- **Built but never used:** `FindingRemediationPanel.tsx` (T-0111: automated desired state and
  command, preconditions, manual portal path and steps) says *"mount it in EPIC-004's finding
  drawer when that lands"*, and nothing mounts it. `ApplyActionDialog.tsx` is not mounted on any
  page either. Most of the per-finding remediation UI already exists and is not connected.
- Remediation and Remediation history are two separate nav items (see T-0920).

## Fix direction

- Add a **finding drawer** to the run's Findings tab. Clicking a finding opens its details
  (current and recommended value, evidence, framework mappings) with `FindingRemediationPanel`
  under them.
- From the drawer, an automated finding offers **Remediate** (through `ApplyActionDialog`,
  then `POST /v1/remediation/.../apply`, then verify). A manual finding shows the steps and
  **Mark as remediated**.
- Add **bulk remediation** on the Findings tab: select several Fail or Warning rows, then
  "Remediate selected", which creates a plan from the selection.
- Add a **Remediation tab** on the run detail with that run's plan, its progress and the
  history of actions taken against the run's findings. This replaces the jump to the separate
  page.
- **Keep the top-level Remediation page** (operator decision, 2026-11-19). It is mostly built
  already and gives one view of open items across runs and tenants. The run detail page gets
  remediation in addition, not instead. Both use the same plan and apply routes, so an action
  taken in either place shows up in the other.
- A re-run or verify should update each finding's state (open, remediated, verified or
  accepted risk) in the run view.

## Acceptance

- [x] Clicking a finding on the run's Findings tab opens a drawer with its details and its
      remediation options.
- [x] An automated finding can be remediated and verified from the drawer, with write
      permissions granted (T-0917). A manual finding shows its steps and can be marked done.
- [x] Several findings can be selected and remediated together from the Findings tab.
- [x] The run detail shows the run's remediation progress and history without leaving the page.
- [x] The Remediation page stays, and actions taken from a run show up on it (and the reverse).
- [x] No file outside `scope` is modified.

## Fix

**Status: fixed-unverified** (2026-11-20)

### Changes

- `portal/web/src/components/RunDetailTabs.tsx`
  - Findings tab: rows are now keyboard-operable (`tabIndex`, Enter/Space) and open a
    right-hand drawer (`role="dialog"`, `aria-modal`, focus trap, Escape to close, focus
    restored to the row). The drawer shows current/recommended value, evidence, framework
    mappings, and `FindingRemediationPanel` underneath.
  - Added the remediation state column (`Open`, `Remediated`, `Verified`, `Accepted risk`).
    State is derived from the run's plan action, then the shared tenant action history, then
    a local mark; a passing verify marks `Verified`, a failing verify leaves the finding
    `Open`.
  - Automated findings: **Remediate** ensures a plan exists and opens `ApplyActionDialog`,
    which posts to the existing `POST /v1/remediation/plans/:planId/apply`; once the action
    is `applied`, **Verify** posts to `POST /v1/remediation/actions/:actionId/verify`.
  - Manual findings: `FindingRemediationPanel` shows the portal path and numbered steps, with
    **Mark as remediated** and **Accept risk** actions.
  - Bulk selection: a checkbox per remediable (Fail/Warning/Review) row plus select-all and
    **Remediate selected**, which creates/loads the run plan and restricts the apply to the
    selected findings' `actionIds`.
  - New **Remediation** tab: progress counts and bar, the run's plan with per-action Apply and
    Verify, and the action history filtered to the run's check ids. It reads and writes the
    same plan/history/apply/verify routes as the top-level page.
  - The chosen plan id is remembered per run in `sessionStorage`; `?planId=` seeds it. The
    "Plan remediation" link is preserved.
- `portal/web/src/app/runs/[id]/page.tsx`
  - Reads `?planId=`, resolves `Remediation.Apply`, passes both to `RunDetailTabs`, and
    passes `fetchRunData` so a verify/manual mark can refresh the run's findings.
- `portal/web/src/components/remediation/RemediationView.tsx`
  - Added **Open in run** (`/runs/:runId?planId=:planId`) so a plan opened on the top-level
    page returns to the same plan in the run's Remediation tab. The page and nav item are
    otherwise unchanged.

### Notes / limitations

- `POST /v1/remediation/plans` accepts only `tenantId` and `runId`, so "remediate selected"
  generates the run-scoped plan and applies only the selected actions via `actionIds`; it
  cannot create a plan containing only the selection without a BFF change.
- There is no BFF endpoint to persist a manual "mark as remediated" or an accepted risk.
  Those marks are stored per run in `sessionStorage` and update the run view immediately;
  a future route is needed for them to survive a browser change or appear in tenant history.
  Automated apply and verify results do persist through the existing routes and appear in
  both views.
