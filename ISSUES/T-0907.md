# T-0907 — Fix pre-existing PowerShell lint findings in Invoke-DomainAction and Linux-only tests

## Report

Two pre-existing `PSScriptAnalyzer` issues remain across PowerShell sources:

1. `portal/workers/M365Portal.Workers/Invoke-DomainAction.ps1` uses `$Error` as a parameter name and exports `Verify-Domain` (unapproved verb; cannot be renamed silently because `tests/Portal/Workers/Invoke-DomainAction.Tests.ps1` asserts `Get-Command Verify-Domain` and invokes it directly).
2. Linux-only Pester tests use `ps` aliases instead of full `Get-Process` / native invocation conventions per `.claude/rules/powershell.md`.

## Fix direction

Update `Invoke-DomainAction.ps1`, module exports (if applicable), and `tests/Portal/Workers/Invoke-DomainAction.Tests.ps1` in lockstep (e.g., rename `$Error` parameter to `$ErrorMessage` / `$ErrorDetail`, replace `Verify-Domain` with `Confirm-Domain` or `Test-DomainVerification` and update tests/callers), and eliminate `ps` alias lint findings in Linux-only tests.

## Acceptance

- [x] `Invoke-DomainAction.ps1` has zero `PSScriptAnalyzer` automatic-variable or unapproved-verb warnings.
- [x] `tests/Portal/Workers/Invoke-DomainAction.Tests.ps1` and module exports remain green with updated function/parameter names.
- [x] Linux-only tests pass `PSScriptAnalyzer` alias checks.
- [x] No file outside `scope` is modified.

## Fix

Changed files:

- `portal/workers/M365Portal.Workers/Invoke-DomainAction.ps1`
  - Renamed the `$Error` parameter to `$ErrorDetail` in `New-DomainActionAudit` and
    `New-DomainActionResult`, including their comment-based help and all 16 call
    sites (`-Error` → `-ErrorDetail`). The emitted audit/result contracts keep the
    serialized `error` property, so the JSON shape is unchanged.
  - Renamed `Verify-Domain` to `Confirm-Domain` (approved verb), updated the
    `Invoke-DomainAction` `'verify'` dispatcher, the `.EXAMPLE`, and the
    `Add-Domain` description reference. The action name `verify` and every result
    field are unchanged, so externally visible behaviour is identical.
- `tests/Portal/Workers/Invoke-DomainAction.Tests.ps1` — updated the four
  `Verify-Domain` references (`Get-Command` assertion plus the three direct
  invocations) to `Confirm-Domain`.
- `tests/Portal/Workers/Invoke-ReportRender.Tests.ps1` — `& ps -eo args` →
  `& /bin/ps -eo args` (native invocation, no `ps` alias).
- `tests/Portal/Workers/Invoke-SandboxedScript.Tests.ps1` — same `/bin/ps`
  change.

No change was needed in `M365Portal.Workers.psm1` / `.psd1`: the domain worker
functions are not module exports (the `domain-action.ps1` entrypoint dot-sources
`Invoke-DomainAction.ps1` and calls `Invoke-DomainAction`, not `Verify-Domain`).

Verification:

- `Invoke-ScriptAnalyzer -Settings ./PSScriptAnalyzerSettings.psd1 -Severity Warning`
  on `Invoke-DomainAction.ps1`, `M365Portal.Workers.psm1`, and
  `M365Portal.Workers.psd1`: 0 findings.
- `PSAvoidUsingCmdletAliases` on `Invoke-ReportRender.Tests.ps1` and
  `Invoke-SandboxedScript.Tests.ps1`: 0 findings.
- `Invoke-Pester tests/Portal/Workers/Invoke-DomainAction.Tests.ps1`: 27 passed,
  0 failed, 0 skipped.
- `Invoke-Pester tests/Portal/Workers/Invoke-SandboxedScript.Tests.ps1`: 18
  passed, 0 failed, 1 skipped (Linux-only resource-limit test).
- `Invoke-Pester tests/Portal/Workers/Invoke-ReportRender.Tests.ps1`: 4 passed,
  6 skipped, 2 failed — the two failures are pre-existing on Windows
  (`chmod` is not available in `New-StubChromium`), unrelated to this ticket's
  alias change and outside its scope.
