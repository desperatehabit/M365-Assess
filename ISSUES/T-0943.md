# T-0943 — Run progress never receives live section events, so the bar is static and shows no step counts

## Report

The run progress UI gives the operator no sense of movement or remaining work.

- `portal/web/src/components/RunsTable.tsx:87-103` — `calculateProgressPercentage` returns 50 for a `running` run that has no progress payload, returns 100 for every non-`queued`/non-`running` status, and the Progress cell is a bare 100px bar with only a `title` tooltip (`RunsTable.tsx:704-708`). There is no percentage text and no `completed / total` count.
- `portal/web/src/components/QueueTracker.tsx:87-117` — the same fallback logic. The drawer shows `Overall Progress {pct}%` (`QueueTracker.tsx:640-672`) and per-section `{completed} / {total} tasks` only when the worker sent those fields; otherwise the bar sits still. `isRunActive` accepts only `running`/`queued` (`QueueTracker.tsx:87-90`), so a run that ends `partial` or `failed` disappears without showing its final state.
- The worker already has a progress bridge, but it is never registered: `portal/workers/M365Portal.Workers/Write-RunProgress.ps1:246-355` defines `Register-RunProgressBridge` / `Complete-RunProgressBridge`, and the module exports them (`M365Portal.Workers.psm1:400-404`), yet `run-tenant.ps1:93-120` and `Invoke-WorkerAssessment` (`M365Portal.Workers.psm1:372-382`) never call them. No `ProgressEvent` JSON reaches `supervisor.ts:169-190`, which already forwards such lines.
- Observed on run `b4d11871-d1c2-4857-8b91-b7c79282af21` (2026-11-23): all 13 `run_sections` rows were written at ingestion with `startedAt = null` and the same `finishedAt` as the run, so the UI had no live section data. The bar stayed static at the fallback value, then the run left the active queue at `partial`/`failed`.

## Fix direction

- Register the progress bridge around `Invoke-WorkerAssessment` with the run, job, and tenant ids, and call `Complete-RunProgressBridge` in `finally` with the real outcome.
- Emit a `running` event when each requested section starts and a terminal event when it ends, plus one run-level terminal event. Seed `Total` from the requested section count so `completed`/`total` is meaningful even when a section has no checks.
- Keep the existing stdout contract: one compact JSON event per line with a monotonic sequence; diagnostics must not share stdout while the bridge is active.
- Runs list: render `{completed} / {total} sections` and the percentage beside the bar, and give `queued`, `running`, `partial`, and `failed` distinct bar states.
- QueueTracker: show the current section and sections remaining; keep a finished run visible until dismissed (or for a short grace period) so the operator sees the final state and issue count.
- Derive progress from persisted `run_sections` as a fallback when no live events arrived, instead of defaulting to 50%.

## Acceptance

- [ ] A running assessment shows an advancing `x of y sections` count and the current section.
- [ ] The Runs list Progress cell shows a percentage and a section count, not only a bar.
- [ ] A run with no live events derives progress from persisted sections instead of showing a fixed 50%.
- [ ] A partial/failed run remains visible in QueueTracker with its final state and issue count.
- [ ] Tests cover bridge registration, section start/finish events, and the no-event fallback; they fail without the change.
- [ ] No file outside `scope` is modified.
