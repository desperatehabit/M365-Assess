# T-0549 — Alerts page and check-alerts view

## Report

EPIC-028 SPEC.md §3.3 defines the **Alerts** page (source/severity/status/entity and row
actions), §3.4 defines **Check Alerts** — the module's own alert findings shown alongside tenant
alerts so analysts see portal-detected issues in the same view. §6 exposes `GET
/v1/check-alerts`. §11 item 3 is **deferred**: auto-incident creation from check alerts is handed
to EPIC-029; the check-alerts surface here is **read-only** (snooze/resolve are EPIC-029).

Deliver the `GET /v1/check-alerts` route (validating authentication only; module-wide, not
tenant-scoped) returning the module's check-alert findings, plus the Alerts page rendering
`AlertsTable` (driving the T-0548 API) with the triage actions handed off to the alert triage
surfaces, and the `CheckAlertsPanel` view that lists check alerts alongside tenant alerts. No
auto-incident creation and no snooze/resolve here. Extend `portal.v1.yaml`.

## Acceptance

- [ ] `GET /v1/check-alerts` returns module check alerts; the endpoint performs no writes.
- [ ] The Alerts page renders the §3.3 table and routes triage actions to T-0548.
- [ ] Check alerts render alongside tenant alerts; auto-incident creation is absent (deferred to EPIC-029).
- [ ] A test covers the check-alerts route and Alerts page render and fails without it.
- [ ] No file outside `scope` is modified.
