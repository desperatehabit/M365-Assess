# T-0899 — /v1/api-clients CRUD and rotate-secret perform no authorization check

## Report

Found while building the T-0893 route-permission probe: the API-client CRUD routes and `rotate-secret` neither check a permission in the handler nor are wrapped by `guardRoute` in `app.ts`, so a caller with no role reaches them. Wrap them with `guardRoute` using the registry permission (register it in `PermissionRegistry`), and add a route-permissions test that a no-role caller gets 403 and the correct roles pass.

## Acceptance

- [ ] The behaviour described in the report is fixed.
- [ ] A test covers it and fails without the fix.
- [ ] No file outside `scope` is modified.

## Resolution notes

- `PermissionRegistry` already carried `CIPP.ApiClients.Read` (list/get) and
  `CIPP.ApiClients.ReadWrite` (create/update/delete/rotate-secret), but `app.ts`
  mounted `createApiClientRoutes` unwrapped. Each route is now passed through
  `guardRoute` with the permission resolved from the registry
  (`permissionForEndpoint`), so an anonymous caller gets 401 and a caller with no
  role gets the structured 403 naming the permission.
- `route-permissions.test.ts` now includes `/v1/api-clients` in the area sweep and
  has a focused block that asserts all six routes are mounted, a no-role caller is
  denied, readonly gets reads, and editor gets reads plus writes. The no-role
  assertions fail without the `app.ts` change.
- Verification: `route-permissions`, `permissions`, and `api-clients` tests pass
  (58 tests). The full BFF suite stays at its documented 21 pre-existing failures;
  no failures are in the API-client or RBAC files.
- `needs_scope_review` stays false: the change is confined to `app.ts` and
  `rbac/route-permissions.test.ts`.
