# T-0063 — Dashboard layout persistence and load/save endpoints

## Report

EPIC-004 SPEC.md §5 defines `DashboardLayout` with `userId`, `scope(global|tenant)`,
`tenantId?`, and `widgets[]` (widget id, position, size, settings); §4.3 says layout changes save
to user preferences with a **Reset to default**. §11.2 adopts **per user + tenant** scope.

Deliver:

- A numbered, forward-only migration (`0002_dashboard_layout.sql`) for the layout table, with
  `createdAt`/`updatedAt` per `03-database.md` §5.
- `portal/db/src/dashboard-layout-repository.ts` that enforces user ownership of a layout and
  returns the stock default when no row exists (reset-to-default).
- `GET`/`PUT /v1/dashboard/layout` handlers filtered by the caller's identity, plus OpenAPI.
- Tests for default fallback, save/reload round-trip, and reset.

## Acceptance

- [ ] A saved layout reloads intact for the same user/tenant and falls back to default for another.
- [ ] Reset to default restores the stock layout.
- [ ] The layout is user-owned; one user cannot read or overwrite another's layout.
- [ ] The migration applies once and is re-runnable.
- [ ] No file outside `scope` is modified.
