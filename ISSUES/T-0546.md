# T-0546 — Incident assign, status, classify, and comment actions

## Report

EPIC-028 SPEC.md §2 US-3, §4.1, and §6 define triage: status (`new` → `in progress` →
`resolved`), classification (true/false positive, informational), assignee, and comments. §6
exposes `POST /v1/tenants/{id}/incidents/{incidentId}/{action}`. §8 routes writes through
**EPIC-006** (confirmation for bulk, before/after, audit). §9 requires that bulk changes never
silently auto-resolve and are audited. §11 item 1 is resolved (adopted): **write-back of status
and classification where the Graph/Defender API supports it**, read-only elsewhere; portal notes
and every change persist via T-0541.

Deliver an `Invoke-IncidentAction.ps1` handler (entrypoint `invoke-incident-action.ps1`) for
assign, status, classify, and comment: where the API supports a field it writes back, otherwise
it records a portal-only note/state change; writes route through the EPIC-006 gated executor
(T-0108). The route validates `incidents.triage` + `Remediation.Apply`, requires confirmation for
bulk changes, and records an `AlertStateChange` with from/to/by/reason. Extend `portal.v1.yaml`.

## Acceptance

- [ ] Assign, status, classify, and comment apply; API-unsupported fields fall back to portal notes only.
- [ ] Each change records an `AlertStateChange` (from/to/by/at/reason) and an audit event.
- [ ] Bulk status changes require confirmation and can never silently auto-resolve.
- [ ] A test covers a supported write-back and an unsupported field fallback and fails without it.
- [ ] No file outside `scope` is modified.
