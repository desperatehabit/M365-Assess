# T-0945 — Run detail and report builder show only the first 100 findings

## Report

`GET /v1/runs/{runId}/results` is cursor-paginated (`bff/src/pagination.ts`: default limit 100,
max 1000) and returns `items`, `total` and `nextCursor`. Two web callers read `items` from the
first response and ignore `nextCursor`:

- `portal/web/src/app/runs/[id]/page.tsx` (`fetchRunData`): the Findings tab, findings filters,
  the finding drawer and bulk remediation all work on the first page only.
- `portal/web/src/app/reports/builder/page.tsx` (`loadRunPreview`): the report preview is built
  from the first page only.

Observed 2026-11-24 on run `b4d11871-d1c2-4857-8b91-b7c79282af21`: the database holds 258
findings and the tab reads `Findings (100)`. The default request returns `items: 100,
total: 258, nextCursor: "MTAw"`. 158 findings (61%) were not visible in the UI.

## Fix direction

- Add one results client (`fetchAllRunResults`) that requests `limit=1000` and follows
  `nextCursor` to the end, taking the issue log from the first page, with a page cap and a
  repeated-cursor guard.
- Use it in both callers.

## Acceptance

- [x] The run detail Findings tab shows every finding (258 for the observed run).
- [x] The report builder preview reads every finding of the selected run.
- [x] Tests cover multi-page reads, an error status, a repeating cursor and the page cap, and fail without the change.
- [ ] Verified on the live portal: run `b4d11871` shows `Findings (258)`.
