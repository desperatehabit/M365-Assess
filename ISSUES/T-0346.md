# T-0346 — BitLocker recovery key search with audited reveal

## Report

EPIC-018 SPEC.md §2 US-4 and §3.4 define **BitLocker Search**: find a device's recovery key(s),
where key display is time-limited and audited. §4.2 requires every reveal to be audited with actor,
device, and timestamp and that values are **never persisted**. §5 adds `KeyAccessAudit` (`id`,
`tenantId`, `deviceId`, `keyType`, `actor`, `at`) and §6 fixes
`GET /v1/tenants/{id}/devices/{deviceId}/bitlocker`.

Deliver migration `0045_key_access_audit.sql` + a `key-access-audit.ts` repository (append-only),
a `Get-BitLockerKeys.ps1` + entrypoint, and the route behind the high-privilege RBAC `devices.keys`
permission. The worker returns key material in the response only; it is not written to the
database, logs, or artifacts, and each retrieval appends a `KeyAccessAudit` row.

## Acceptance

- [ ] `GET /v1/tenants/{id}/devices/{deviceId}/bitlocker` returns the device's recovery key(s) and metadata.
- [ ] Every retrieval appends a `KeyAccessAudit` row with actor, device, key type, and timestamp.
- [ ] No key value is persisted by the portal or written to logs.
- [ ] Tests cover the route and worker and fail without them.
- [ ] No file outside `scope` is modified.
