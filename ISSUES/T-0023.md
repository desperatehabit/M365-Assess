# T-0023 — Credential store, set/rotate, and expiry states

## Report

EPIC-002 SPEC.md §6 requires `POST /v1/tenants/{id}/credential` to set or rotate a tenant
credential, and §5/§7 make `tenants.credentials` admin-only. `03-database.md` §4 is explicit:
the DB stores a `secretRef` reference only, never the secret; cert auth is preferred over
client secrets; and the credential record carries `tenantId`, `authMethod`, `clientId`,
`secretRef`, `thumbprint`, `environment`, `expiresOn`, `lastValidated`. §4.5 fixes expiry
semantics: a credential is `expiring` at ≤30 days and `expired` thereafter, feeding EPIC-029
alerts.

Deliver a credential-store interface plus an OS-keystore implementation (dev; Key Vault is a
later same-interface backend), the set/rotate route that writes only a reference, and an
`expiry.ts` that derives `valid`/`expiring`/`expired`/`missing`. Reuse the T-0011
`Resolve-TenantCredential` contract so stored material stays resolvable only in the worker.

## Acceptance

- [ ] Set/rotate persists a `secretRef` and returns no secret value; EXO/Purview reject a
      client secret with a clear error.
- [ ] A test asserts no API response, log, or DB row contains the secret value.
- [ ] Expiry derivation covers `valid`, `expiring` (≤30 days), `expired`, and `missing`.
- [ ] Every credential mutation writes an audit event.
- [ ] No file outside `scope` is modified.
