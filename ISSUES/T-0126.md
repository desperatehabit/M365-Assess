# T-0126 — Sandboxed custom-script execution

## Report

EPIC-007 SPEC.md §4.3 step 4 and §8 require that a custom script executes inside a sandbox:
restricted cmdlet/type allowlist, no filesystem/network beyond the tenant connections, resource
limits, and a timeout; "a script that cannot be sandboxed is rejected." §11.2 resolves the
sandbox to a **constrained child process + allowlist**. §9 risk "arbitrary code execution" is the
top risk this ticket mitigates. §7 says scripts run in the tenant's child process.

Deliver:

- `Invoke-SandboxedScript.ps1`: launches a constrained `pwsh` child with a restricted
  `InitialSessionState`/language mode and an explicit cmdlet/type allowlist, enforcing CPU/memory
  and wall-clock limits, with no `Invoke-Expression` on untrusted input.
- Admit/deny policy: a script referencing a disallowed command or type is rejected **before**
  execution (fail closed).
- Pester tests: an allowed script runs; a disallowed cmdlet fails closed; a runaway script is
  killed by the timeout.

Note: writes performed by a script must route through the EPIC-006 remediation contract (prose
cross-ref); this ticket provides the sandbox execution primitive only.

## Acceptance

- [ ] A permitted script runs and returns its output; a disallowed cmdlet is blocked.
- [ ] A script exceeding the resource/time limit is terminated and reported failed.
- [ ] A script that cannot be sandboxed is rejected, not run unsandboxed.
- [ ] A test covers the change and fails without it.
- [ ] No file outside `scope` is modified.
