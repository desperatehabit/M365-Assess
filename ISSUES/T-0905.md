# T-0905 — Persist webhook clientState and mount POST /v1/webhooks/notify

## Report

`portal/db/migrations/0040_audit_logs_webhooks.sql` defines `webhook_subscriptions (id, tenantId, resource, expiresOn, state, notificationUrl, createdAt, updatedAt)` without a `clientState` (or hashed `clientState`) column. Because Graph change-notification validation and `clientState` authenticity checks depend on persisting the per-subscription secret state, `T-0862` left `POST /v1/webhooks/notify` unmounted (`portal/bff/src/routes/webhooks.ts`) to avoid accepting unverified webhook callbacks.

## Fix direction

1. Add a SQLite migration adding `clientStateHash` (or encrypted `clientState`) to `webhook_subscriptions`.
2. Persist and verify `clientState` in `SqliteAuditRepository` and `portal/bff/src/adapters/audit.ts`.
3. Mount `POST /v1/webhooks/notify` in `portal/bff/src/app.ts` and register it in `permissions.ts` / `openapi.ts` / `portal.v1.yaml`.

## Acceptance

- [x] A database migration persists per-subscription `clientState` verification state cleanly across upgrades.
- [x] `POST /v1/webhooks/notify` handles Graph validation tokens and rejects missing/mismatched `clientState` payloads.
- [x] Integration tests cover subscription creation, valid callback delivery, and invalid `clientState` rejection.
- [x] No file outside `scope` is modified.

## Fix

### Storage

- Added forward-only migration `portal/db/migrations/0131_webhook_client_state.sql`: `ALTER TABLE webhook_subscriptions ADD COLUMN clientStateHash TEXT`. Migration `0040` was not touched. Rows created before 0131 keep `NULL` and their callbacks fail closed until the subscription is recreated with a clientState.
- Only a SHA-256 hash is stored, matching the `api_clients.secretHash` precedent; there is no plaintext clientState column.
- `WebhookSubscription` (`repository.ts`) gained `clientStateHash: string | null`; `WebhookSubscriptionInput` accepts the worker's plaintext `clientState` and hashes it in `SqliteAuditRepository`. `WebhookSubscriptionUpdate` does the same for create/recreate mirroring without clobbering the hash on renew.
- Added `AuditRepository.getWebhookSubscriptionById(id)` so the receiver can resolve a subscription from Graph's subscription id without a tenant parameter.

### Adapter and receiver

- `portal/bff/src/adapters/audit-logs.ts` now forwards the worker's `clientState` when mirroring create/recreate results into the repository; renew passes none, so the stored hash survives.
- `portal/bff/src/routes/webhook-notify.ts` compares a SHA-256 hash of each callback's `clientState` to the stored hash with a constant-time comparison. A missing or mismatched value is `401 webhooks.notify_invalid_client_state`; the Graph `validationToken` handshake still answers `200 text/plain` with no auth. The plaintext is no longer forwarded to the dispatch seam, and the OpenAPI fragment documents the handshake query parameter.

### Mount and registrations

- `portal/bff/src/app.ts` mounts `createWebhookNotifyRoute` with a repository-backed `WebhookNotifyStore` and an acceptance-audit dispatcher. It deliberately passes no `resolveCaller`/`authorize`: the existing per-route auth seam only runs when a route asks for a caller, and Graph cannot carry a portal session. `clientState` is the credential (SPEC §4.3), so the receiver is genuinely unauthenticated; this choice is documented at both the mount and the route module.
- `permissions.ts` registers `POST /v1/webhooks/notify` as `Public`; `openapi.ts` includes the `WEBHOOK_NOTIFY_OPENAPI` fragment; `portal/contracts/openapi/portal.v1.yaml` was regenerated with the temp-test recipe and the drift test passes.
- Content-bundle processing remains deferred (SPEC §11.2); accepted notifications are recorded as audit events and dispatch stays a no-op until the EPIC-029 alert/cache seam is wired.
