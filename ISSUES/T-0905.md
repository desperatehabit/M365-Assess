# T-0905 — Persist webhook clientState and mount POST /v1/webhooks/notify

## Report

`portal/db/migrations/0040_audit_logs_webhooks.sql` defines `webhook_subscriptions (id, tenantId, resource, expiresOn, state, notificationUrl, createdAt, updatedAt)` without a `clientState` (or hashed `clientState`) column. Because Graph change-notification validation and `clientState` authenticity checks depend on persisting the per-subscription secret state, `T-0862` left `POST /v1/webhooks/notify` unmounted (`portal/bff/src/routes/webhooks.ts`) to avoid accepting unverified webhook callbacks.

## Fix direction

1. Add a SQLite migration adding `clientStateHash` (or encrypted `clientState`) to `webhook_subscriptions`.
2. Persist and verify `clientState` in `SqliteAuditRepository` and `portal/bff/src/adapters/audit.ts`.
3. Mount `POST /v1/webhooks/notify` in `portal/bff/src/app.ts` and register it in `permissions.ts` / `openapi.ts` / `portal.v1.yaml`.

## Acceptance

- [ ] A database migration persists per-subscription `clientState` verification state cleanly across upgrades.
- [ ] `POST /v1/webhooks/notify` handles Graph validation tokens and rejects missing/mismatched `clientState` payloads.
- [ ] Integration tests cover subscription creation, valid callback delivery, and invalid `clientState` rejection.
- [ ] No file outside `scope` is modified.
