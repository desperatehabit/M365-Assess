# T-0854 — Mount and deliver EPIC-024 Email Tools routes and Message Viewer

## Report

The EPIC-024 factories (`createMessageTraceRoutes`, `createHistoricalSearchRoutes`,
`createMessageRoutes`, `createMailRestoreRoutes`, `createEncryptionRoutes`) exist under
`portal/bff/src/routes/` and are tested, but `portal/bff/src/app.ts` imports none of them and there is
no adapter under `portal/bff/src/adapters/`, so the endpoints 404. Workers
(`get-message-trace.ps1`, `get-message-detail.ps1`, `start-historical-search.ps1`,
`start-mailbox-restore.ps1`, `get-message-encryption.ps1`) and migration `0032_mail_restore_jobs.sql`
exist.

UI: `portal/web/src/components/email-tools/MessageViewer.tsx` exists but is imported by no page, and
no web code calls `GET /v1/tenants/{id}/mail/messages/{messageId}` (SPEC §3.3, §10). Message trace,
historical search, restores, and encryption pages exist under `app/tools/email/`.

## Acceptance

- [x] Every EPIC-024 SPEC §6 endpoint returns a non-404 response from a running BFF.
- [x] Message trace, historical search, restores, encryption, and message detail run their real workers.
- [x] The Message Viewer is reachable from the email tools UI and renders live message data.
- [x] No file outside `scope` is modified.

## Fix

`createEmailToolsProviders` binds the five worker-backed seams to their existing
entrypoints. Trace, historical search, message detail, restore, and encryption
calls all carry the tenant credential block, so the BFF never reaches EXO itself:

- `get-message-trace.ps1` receives the T-0007 envelope with the §3.1 filters,
  page size, and cursor; its empty-string last-page cursor is normalized to
  `null`.
- `start-historical-search.ps1` runs the `start`, `poll`, and `cancel` actions
  behind a BFF-generated job id; the worker's flattened job record is mapped to
  the route's job/result shapes.
- `get-message-detail.ps1` receives `messageId` and `includeBody`; an unknown
  message maps to the route's 404 rather than a worker 502.
- `start-mailbox-restore.ps1` plans with `dryRun` and applies with
  `confirmed`; the applied RestoreJob persists through the shared repository
  (migration 0032) and progress reads come back from that row.
- `get-message-encryption.ps1` reads the IRM/OME configuration and previews or
  applies an OME template change (the worker reads `action` at the envelope's
  top level, so the adapter builds the envelope rather than using
  `createEnvelopeWorker`).

`createApp` mounts all five route groups behind `resolveCaller`, the shared
authorizer, and the audit sink. Trace reads accept `Exchange.MailTools.Read` or
`Exchange.MailSearch.Execute`; an OME template change accepts
`Exchange.MailTools.ReadWrite` or `Remediation.Apply`. Every endpoint is
registered in the EPIC-038 permission registry, published through its OpenAPI
fragment, and the checked-in contract is regenerated.

The message viewer now renders at `portal/web/src/app/tools/email/message-viewer`
and reads `GET /v1/tenants/{id}/mail/messages/{messageId}`. The trace worker
also emits the message identity (`MessageTraceId`/`InternetMessageId`) on each
row, so the table's existing "View details" link carries a `messageId` into the
viewer; when a trace row has no identity the viewer asks for one instead of
calling the BFF with a made-up message.
