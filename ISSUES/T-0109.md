# T-0109 — Verify after apply and flip the finding

## Report

EPIC-006 SPEC.md §4.4 resolves verify: after apply, re-run the affected collector for the check
and update the finding; success sets the action `applied` and re-evaluates the finding, while
failure/partial sets `failed` and raises an alert. SPEC.md §11 item 5 resolves the scope:
**single-check re-collection where the collector supports it, otherwise re-run the whole
section.** `POST /v1/remediation/actions/{actionId}/verify` (SPEC §6) triggers this.

Add an `Invoke-RemediationVerify.ps1` worker job that chooses single-check re-collection when
the collector exposes it and falls back to a section re-run, then updates the `RemediationAction`
state and the finding via the EPIC-001 run persistence (T-0012) and writes an `AuditEvent`.
Verify is itself read-only against the tenant. Extend the BFF route from T-0108.

## Acceptance

- [ ] A remediated finding flips to `Pass` and its action becomes `applied`.
- [ ] A still-failing check leaves the finding and records the action `failed` with an alert.
- [ ] Single-check re-collection is used when available; otherwise the section re-runs; both paths are tested.
- [ ] Every verify writes an `AuditEvent`.
- [ ] A test covers the change and fails without it.
- [ ] No file outside `scope` is modified.
