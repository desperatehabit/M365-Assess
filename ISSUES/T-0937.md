# T-0937 — Collectors that skipped or failed are logged as `Complete`

## Report

In the walk's run:
- **Teams Security Config** logs "Teams Graph APIs do not support app-only… Skipping Teams
  collector", but the summary CSV records it as `Complete, 0 items`.
- No Teams checks appear at all, not even as Skipped.
- `21-Teams-Access.csv` is all `N/A`.
- **Power BI** is recorded as `Complete`, although its API call failed (T-0936).

A reader of the summary, and the portal (T-0929), sees these sections as having run cleanly.

## Fix direction

- Give the summary a collector status beyond Complete: `Skipped (reason)`, `Partial` and
  `Failed`. Have collectors report their own outcome to the orchestrator.
- For Teams, either connect the MicrosoftTeams module with certificate app-only auth and run
  the checks, or emit each Teams check as `Skipped` with "app-only not supported".
- Feed collector status into the run's section status in the portal (T-0929).

## Acceptance

- [x] A collector that skips or fails is never logged as `Complete`.
- [x] Teams checks are either collected or each listed as Skipped with a reason.
- [x] No file outside `scope` is modified.

## Fix

### Status convention (stable, documented)

The summary CSV's `Status` column now carries exactly one of four values. The second
comment line of `_Assessment-Summary*.csv` documents the vocabulary in the file itself,
and the reason for any non-`Complete` collector travels in the `Error` column:

| Status | Meaning |
|--------|---------|
| `Complete` | The collector ran and produced its full set of checks. Unchanged for genuinely complete collectors. |
| `Partial` | The collector ran, but at least one source/endpoint was unavailable, so coverage is incomplete. |
| `Skipped` | The collector did not run (app-only auth, no licence, prerequisite not met, operator choice). |
| `Failed` | The collector could not produce usable results (API/permission/role failure). |

### Collector → orchestrator contract

A collector reports its own outcome by emitting a single typed object (it is filtered out
of the section CSV rows):

```powershell
[PSCustomObject]@{
    PSTypeName = 'M365Assess.CollectorOutcome'
    Outcome    = 'Skipped'   # Complete | Partial | Skipped | Failed
    Reason     = 'app-only not supported: ...'
}
```

The property is `Outcome`, not `Status`, so an outcome object can never be mistaken for a
finding (whose `Status` uses the `Add-SecuritySetting` taxonomy; the
`Status-Normalization` behaviour test scans collector files for `Status = '...'` literals).

A child-process collector (Power BI runs in an isolated `pwsh`) cannot return objects to
the parent, so it writes the same shape as JSON to `<csv path>.status.json` beside its CSV;
the orchestrator reads it and deletes it. `Get-CollectorOutcome` validates the value
(unknown statuses fall back to the historical row-count inference), the outcome overrides
that inference, and `Write-CollectorOutcome` puts the reason in the log and adds a WARNING
(`Skipped`/`Partial`) or ERROR (`Failed`) issue so `_Assessment-Issues*.log` and the
portal's Issues tab carry it.

### Teams app-only decision

The MicrosoftTeams module is not a dependency of this module (not in `RequiredModules`,
`Test-ModuleCompatibility`, `Connect-Service`, or the disconnect path), and its app-only
cmdlet coverage is unverified. Rather than add an untested connection path, the ticket's
second option was implemented: every Teams check is emitted as `Skipped` with
"app-only not supported" and the collector is `Skipped`. A tenant with no Teams licences
likewise reports `Skipped` (it previously returned nothing and was logged `Complete`).
