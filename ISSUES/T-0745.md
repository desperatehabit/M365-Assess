# T-0745 — Custom roles CRUD with include/exclude patterns

## Report

EPIC-038 SPEC.md §3.2 and §6: base-role rows are read-only; custom roles are editable.
`GET`/`POST`/`PATCH`/`DELETE /v1/roles` provide role CRUD, with base roles immutable. The role
editor holds two pattern lists (**Include**, **Exclude**) and a **Preview effective permissions**
panel that resolves the include/exclude result against the endpoint permission registry. SPEC.md
§11 item 5 resolves the custom-role ceiling: a custom role **may** include `Remediation.Apply`,
but only assignable by a superadmin and audited.

Add the `roles.ts` route: create/update a custom role's include/exclude patterns, clone a base
role into a custom one, delete only when not in use, and reject any mutation targeting a
`builtin` role. Enforce the §4.1 wildcard semantics through T-0743 and expose the preview
resolution as a read helper the UI (T-0753) calls. A custom role containing `Remediation.Apply`
is accepted but flagged as superadmin-only at assignment (T-0744). Extend `portal.v1.yaml`.

## Acceptance

- [ ] Custom roles create/update/delete; base roles are rejected as mutable.
- [ ] Include/exclude patterns resolve through T-0743 consistently with the UI preview.
- [ ] Deleting a role in use is blocked.
- [ ] A custom role including `Remediation.Apply` is accepted but flagged superadmin-only and audited.
- [ ] A test covers the change and fails without it.
- [ ] No file outside `scope` is modified.
