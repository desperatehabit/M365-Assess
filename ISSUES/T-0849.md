# T-0849 — Mount and deliver EPIC-019 Defender routes with real storage

## Report

`portal/bff/src/routes/defender-{status,deploy,vulnerabilities,mde-onboarding,cve-exceptions,templates}.ts`
define the SPEC §6 endpoints but no factory (`createDefenderStatusRoutes`, `createDefenderDeployRoute`,
`createDefenderVulnerabilitiesRoutes`, `createMdeOnboardingRoutes`, `createDefenderCveExceptionRoutes`,
`createDefenderTemplateRoutes`) is imported in `portal/bff/src/app.ts`; a repo-wide search finds each
only in its own file. `portal/bff/src/adapters/` has no Defender provider, so the endpoints 404 at
runtime. Workers that must back the providers exist (`portal/workers/get-defender-status.ps1`,
`deploy-defender-policies.ps1`, `get-tvm-vulnerabilities.ps1`, `get-mde-onboarding.ps1`).

`portal/bff/src/repository/defender-deployment-templates.ts` also exposes
`createInMemoryDefenderDeploymentTemplateRepository` (`:179`) instead of a SQLite implementation;
migration `portal/db/migrations/0022_defender_deployment_templates.sql` already owns the relational
shape.

UI: `portal/web/src/components/defender/DefenderSetupWizard.tsx` exists but is imported by no page;
there is no `app/security/defender/setup` route (SPEC §3.2). The CVE Report and Device Compliance
report surfaces under Reports (SPEC §3) are absent.

## Fix direction

Add a Defender adapter next to the other worker-backed adapters (`runFeatureWorker` + the tenant
credential block), implement a SQLite `DefenderDeploymentTemplateRepository`, mount all six route
groups in `app.ts` with `ctx.caller`, the shared authorizer, and the audit sink, then render the
setup wizard and the two report surfaces on the existing pages.

## Acceptance

- [x] Every EPIC-019 SPEC §6 endpoint returns a non-404 response from a running BFF.
- [x] The callback-URL deploy, CVE exceptions, vulnerability, and MDE onboarding routes run their real workers.
- [x] Defender deployment templates persist through SQLite, not the in-memory repository.
- [x] The Defender setup wizard renders live data at `/security/defender/setup`; the CVE Management and MDE Onboarding pages render the CVE/Device-Compliance report data.
- [x] A test covers each mounted route and fails without the mount.
- [x] No file outside `scope` is modified.

## Fix

`createDefenderProviders` binds the four worker-backed seams to the existing
entrypoints: `get-defender-status.ps1`, `deploy-defender-policies.ps1` (dry run for
the plan, live for apply, lifting the worker's `templateDraft.policyJson` into the
result the save-as-template path persists), `get-tvm-vulnerabilities.ps1` (CVE list
and device drill-through), and `get-mde-onboarding.ps1`. Every call carries the
tenant credential block, so the BFF never reaches Graph itself.

`SqliteDefenderDeploymentTemplateRepository` implements the T-0363 interface over
migration 0022 with JSON columns, tenant scoping, policy-area filtering, and soft
delete; the in-memory store remains for route tests.

`createApp` mounts all six route groups (status, deploy, vulnerabilities, MDE
onboarding, CVE exceptions, deployment templates) behind the shared authorizer and
audit sink. The deploy route accepts `Security.Defender.ReadWrite` or
`Remediation.Apply`; template routes are guarded by the permission each carries;
CVE exceptions and templates require the tenant to be in caller scope. All paths
are registered in the EPIC-038 permission registry and published through their
OpenAPI fragments, and `portal/contracts/openapi/portal.v1.yaml` is regenerated.

The setup wizard now renders at `portal/web/src/app/security/defender/setup`, using
the existing `DefenderSetupWizard` preview/apply fetch helpers. The CVE Management
and MDE Onboarding pages already render the CVE and device-coverage surfaces from
live worker data; adding Reports-nav shortcuts remains with T-0887 (AppNav).
