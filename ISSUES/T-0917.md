# T-0917 — Onboarding grants read-only access, so every portal write fails

## Report

Onboarding (`Grant-M365AssessConsent`) grants the read-only set in `PermissionDefinitions.ps1`:
Graph `*.Read.All` application permissions, the EXO role groups *View-Only Organization
Management* and *Compliance Management*, and the Entra roles *Compliance Administrator*,
*Security Reader* and *Global Reader*. That is correct for the assessment. The portal's write
workers sign in app-only with the same certificate (`Connect-WorkerTenant`), so every write
check in the Phase 2 runbook (§4 rows marked **W**, and §5) fails with 403 or an EXO
"not authorized" error until the app has the permissions below.

## Write permissions the workers call for

Built on 2026-11-19 from the `POST`/`PATCH`/`PUT`/`DELETE` Graph calls and the EXO write cmdlets
in `portal/workers/M365Portal.Workers/`. All are **application** permissions on Microsoft Graph
unless marked.

### Not covered by any permission (check live and file a ticket if they fail)
- **Webhook subscriptions** (`Manage-WebhookSubscription`, T-0902) need the read permission for the
  subscribed resource, which the read-only set may already have. Some resources need a public
  notification URL that a local BFF does not have.
- **Connection gaps:** `Connect-WorkerTenant` opens only Graph and Exchange Online.
  - `Start-HistoricalSearch` calls `New-ComplianceSearch`, which exists only in a Security &
    Compliance session (`Connect-IPPSSession`), not in the Exchange session.
  - `Invoke-TeamsVoice` calls `*-Cs*` cmdlets, but no worker connects MicrosoftTeams.
  - Both are expected to fail no matter which permissions are granted.
- `Invoke-LisLocation` calls `/v1.0/communications/lis/locations`. That path was not found in
  Microsoft Graph v1.0 and needs checking.

## Fix direction

The assessment app must stay read-only. Two options:

1. **Second app registration** (`M365-Assess-Operator`) with the write set, created by an opt-in
   step in the wizard. Write workers use its credential and read workers keep the reader app.
2. **Opt-in write mode** on the existing app: `Grant-M365AssessConsent -IncludeWritePermissions`,
   driven by a checkbox in the wizard.

Both should let the operator choose groups of permissions (for example identity, Intune, email,
SharePoint) rather than all of them, and should flag the dangerous ones (PIM role assignment,
device wipe, `Sites.FullControl.All`).

**Phase 2 interim (test tenant only):** in Entra, add the permissions above to the onboarded
app, grant admin consent, and assign it the Exchange Administrator role. Remove them after the
walk.

## Acceptance

- [ ] The reader app's permissions are unchanged when write access is not chosen.
