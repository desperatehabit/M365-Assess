# T-0917 — Onboarding grants read-only access, so every portal write fails

## Report

Onboarding (`Grant-M365AssessConsent`) grants the read-only set in `PermissionDefinitions.ps1`:
Graph `*.Read.All` application permissions, the EXO role groups *View-Only Organization
Management* and *Compliance Management*, and the Entra roles *Compliance Administrator*,
*Security Reader* and *Global Reader*. That is correct for the assessment. The portal's write
workers sign in app-only with the same certificate (`Connect-WorkerTenant`), so every write
check in the Phase 2 runbook (§4 rows marked **W**, and §5) fails with 403 or an EXO
"not authorized" error until the app has the permissions below.

## Write permissions the workers call for

in `portal/workers/M365Portal.Workers/`. All are **application** permissions on Microsoft Graph

### Not covered by any permission (check live and file a ticket if they fail)
- **Webhook subscriptions** (`Manage-WebhookSubscription`, T-0902) need the read permission for the
  subscribed resource, which the read-only set may already have. Some resources need a public
  notification URL that a local BFF does not have.
- **Connection gaps:** `Connect-WorkerTenant` opens only Graph and Exchange Online.
  - `Start-HistoricalSearch` calls `New-ComplianceSearch`, which exists only in a Security &
    Compliance session (`Connect-IPPSSession`), not in the Exchange session.
  - `Invoke-TeamsVoice` calls `*-Cs*` cmdlets, but no worker connects MicrosoftTeams.
  - Both are expected to fail no matter which permissions are granted.
- `Invoke-LisLocation` calls `/v1.0/communications/lis/locations`. That path was not found in
  Microsoft Graph v1.0 and needs checking.

## Fix direction

The assessment app must stay read-only. Two options:

1. **Second app registration** (`M365-Assess-Operator`) with the write set, created by an opt-in
   step in the wizard. Write workers use its credential and read workers keep the reader app.
2. **Opt-in write mode** on the existing app: `Grant-M365AssessConsent -IncludeWritePermissions`,
   driven by a checkbox in the wizard.

Both should let the operator choose groups of permissions (for example identity, Intune, email,
SharePoint) rather than all of them, and should flag the dangerous ones (PIM role assignment,
device wipe, `Sites.FullControl.All`).

**Phase 2 interim (test tenant only):** in Entra, add the permissions above to the onboarded
app, grant admin consent, and assign it the Exchange Administrator role. Remove them after the
walk.

## Design (implemented 2026-11-20)

**Decision: option 1, a second app registration.** The reader app is untouched.

### Onboarding (`Grant-M365AssessConsent`)

- New opt-in parameters: `-IncludeWritePermissions`, `-WritePermissionGroups
  identity|security|intune|sharepoint|exchange`, `-ConfirmDangerous`, and
  `-OperatorAppDisplayName` (default `M365-Assess-Operator`).
- `PermissionDefinitions.ps1` now owns the write matrix as
  `$script:OperatorWriteGroups`, plus `$script:OperatorDangerousPermissions` and the
  built-in `$script:OperatorDirectoryRoleTemplates`. `Get-M365AssessOperatorWriteSelection`
  resolves a selection into Graph permissions, Exchange app roles, EXO role groups, and
  directory roles.
- The operator app reuses the reader certificate (same public key/thumbprint, so the
  returned `operatorCertificateThumbprint` is the reader thumbprint). It is created once
  and resumed on later runs.
- Graph permissions are granted only for the selected groups. `Exchange.ManageAsApp` and
  the Exchange Administrator / eDiscovery Manager / Teams Administrator roles are assigned
  only when `exchange` is selected. EXO role-group membership for Exchange Administrator
  also happens only then.
- `-ConfirmDangerous` is required when a selection contains PIM role assignment
  (`RoleAssignmentSchedule.ReadWrite.Directory`, `RoleEligibilitySchedule.ReadWrite.Directory`),
  device wipe (`DeviceManagementManagedDevices.PrivilegedOperations.All`), or
  `Sites.FullControl.All`. Without it the cmdlet refuses before any mutation and names the
  grants. `-WhatIf` plans the operator grants without contacting a tenant.
- Without `-IncludeWritePermissions` the reader path is byte-for-byte the existing one.

### Storage and worker selection

- Migration `0132_tenant_credential_purpose.sql` adds `tenant_credentials.purpose`
  (`reader` default, forward-only) with an index on `(tenantId, purpose)`.
- The onboarding route stores the operator row beside the reader row with
  `purpose = 'operator'` and never rewrites the reader row. Secret material still lives in
  the credential store; the database holds only `secretRef`.
- Reference shape: reader `tenants/<id>/credential`, operator
  `tenants/<id>/operator-credential`.
- `createTenantWorker` / `createEnvelopeWorker` take an optional
  `{ purpose: "reader" | "operator" }`; omitted means reader. A write job with no operator
  credential fails `409 tenant.operator_credential_missing` and never falls back to the
  reader app.
- `Resolve-TenantCredential` accepts `-Purpose` and validates it against the reference and
  the row; `Connect-WorkerTenant`, `Read-WorkerContextCredential`, and `run-tenant.ps1`
  carry the purpose from the job/context.
- **Remediation apply** is wired end-to-end: the route marks the job `purpose: operator`,
  the queue attaches the operator credential block, and the worker resolves it. Plan and
  verify stay reader. The remaining write adapters are T-0940.

### Wizard

Step 6 has an opt-in "Also grant portal write access" checkbox, the five group chips, a
danger confirmation when identity/Intune/SharePoint is selected, progress text, and a
result panel that states the reader app is unchanged. Declining write access sends no
write fields, so onboarding behaves exactly as before.

### Release note

- Add opt-in portal write access through a separate `M365-Assess-Operator` app registration
  (identity/security/Intune/SharePoint/Exchange groups, dangerous grants confirmed
  separately); the reader app stays read-only.
