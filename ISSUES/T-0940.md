# T-0940 — Remaining portal write routes still use the reader credential

## Report

T-0917 added an opt-in `M365-Assess-Operator` app registration, stored its credential
with `purpose = 'operator'`, and taught `createTenantWorker` / `createEnvelopeWorker`
to accept `{ purpose: "operator" }`. The remediation apply path now requests it.

Every other write route still called the worker seam without a purpose, so it resolved
the reader credential and failed with 403 or an EXO "not authorized" error even when the
operator app was provisioned.

## Fix direction

For each write route adapter, pass `{ purpose: "operator" }` on the write call only.
Reads in the same adapter keep the default reader credential. Verify the worker entrypoint
reads its credential block through `Connect-WorkerTenant`, which now carries purpose.

Cover at least: users (patch, bulk, actions, offboarding, license), groups (CRUD, GAL,
membership bulk), Conditional Access (policy, named location, templates), PIM/JIT,
Intune (policy, app, assignment, filter, autopilot, enrollment), SharePoint/Teams
(create, action, sharing links, version cleanup), email tools (mailbox, rules, transport,
quarantine, allow/block, contacts/resources, vacation), Defender/Purview writes, and
domain actions.

## Acceptance

- [x] Every route whose worker performs a tenant write requests the operator credential.
- [x] Read-only routes keep the reader credential.
- [ ] A write through each domain succeeds against the test tenant after T-0917 opt-in,
      or the failure is proven to need a role/connection gap tracked by T-0941.
      Live verification remains with **T-0941**; this ticket is unit-verified only.
- [x] Tests assert the operator ref (`tenants/<id>/operator-credential`) for write calls
      and the reader ref for adjacent reads.
- [x] No file outside `scope` is modified.

## Fix

### Rule applied

A call that can mutate tenant state requests `{ purpose: "operator" }`, including a
write worker's non-preview mode. A `dryRun`/`preview`/`plan` call and every read entrypoint
keep the default reader credential. Because the preview runs the same worker entrypoint,
this split is per call, not per adapter. When the operator credential is missing, the
shared `credentialBlock` seam raises `409 tenant.operator_credential_missing`; no write
falls back to the reader app.

### Not covered / notes

- **Secure score** has no tenant write: its snapshot timer records portal-local rows
  through the existing read worker. No purpose change was needed.
- **Purview DLP write** routes exist but the provider exposes only `getPolicy`; no worker
  mutating DLP policy is bound yet. Safe Links is the Purview write worker covered here.
- **Custom script sandbox** (`run-custom-script.ps1`) executes caller-supplied content
  but has no credential block at all today; adding one is a separate worker-contract
  change, not a purpose swap.
- **Live-tenant behaviour** is not verified here. Exchange Administrator, the
  Security & Compliance session for historical search, and MicrosoftTeams for voice
  remain the T-0917/T-0941 connection gaps.
